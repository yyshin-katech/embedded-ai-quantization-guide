0.5단계 — 쉬운 방법부터: 배포 난이도 사다리 신규 · 2026 기준

본 로드맵(TensorRT/TIDL/QNN/DRP-AI)은 난이도 최상급입니다. "모델을 임베디드에 올린다"는 감각을 가장 빨리 얻는 순서는 아래 사다리입니다. 각 레벨을 반나절~며칠 안에 끝내고 다음으로 올라가면, 1단계 이후의 본 커리큘럼이 훨씬 수월해집니다.

Lv.1 — Edge Impulse: 가장 쉬운 시작 반나절

  • 웹 UI에서 데이터 수집 → 학습 → 양자화(INT8 TFLite)까지 자동 → 보드용 펌웨어/라이브러리로 원클릭 배포. 최적화 고민 없이 전체 파이프라인을 경험하는 데 최적.
  • 2025년 Qualcomm이 인수하여 Dragonwing 계열 보드 + Hexagon NPU(QNN) 배포까지 공식 지원 — 즉 Lv.1에서 시작해도 나중에 본 가이드의 QNN 트랙과 자연스럽게 연결됨.
  • BYOM(Bring Your Own Model): 직접 만든 ONNX/TFLite 모델을 업로드해 NPU 가속 배포도 가능.
  • 보드: 갖고 있는 Raspberry Pi, Arduino Nano 33 BLE Sense 등 아무거나. 없으면 스마트폰도 타깃이 됨.

Lv.2 — LiteRT (구 TFLite): 코드로 하는 첫 변환 2~3일

  • 2024년 TensorFlow Lite가 LiteRT로 개명 (TFLite Micro → LiteRT Micro). 임베디드 툴체인 중 가장 성숙하고 자료가 많음.
  • 흐름: Keras/TF 모델 → tf.lite.TFLiteConverter → .tflite → Raspberry Pi에서 Python 인터프리터로 추론.
  • 여기서 처음으로 post-training quantization 옵션을 직접 켜보는 것이 핵심 — representative dataset을 넣어 INT8 변환 후 정확도 변화를 눈으로 확인.
converter = tf.lite.TFLiteConverter.from_saved_model(path)
converter.optimizations = [tf.lite.Optimize.DEFAULT]
converter.representative_dataset = rep_data_gen   # ← 1단계 '캘리브레이션' 개념의 축소판
tflite_int8 = converter.convert()

Lv.3 — ONNX Runtime: "한 모델, 여러 하드웨어"의 원형 3~5일

  • PyTorch/TF 어디서 학습했든 ONNX로 내보내면 Execution Provider(EP) 한 줄 교체로 CPU → CUDA → TensorRT EP → QNN EP → OpenVINO를 오갈 수 있음. 지원 하드웨어 폭이 가장 넓은 중립 지대.
  • 본 가이드 4단계(멀티 SoC)의 미니어처 버전: EP를 바꿔가며 latency를 재보면 "같은 ONNX, 다른 백엔드" 감각이 바로 생김.
  • 단, 양자화·NPU 최적화는 벤더 네이티브 런타임(LiteRT/ExecuTorch/벤더 SDK)이 보통 한두 발 앞서 있다는 한계도 함께 체감할 것.

Lv.4 — ExecuTorch: PyTorch 진영의 정식 엣지 경로 1주

  • Meta의 온디바이스 런타임, 2025년 말 v1.0 GA. 기본 풋프린트 ~50KB로 MCU부터 스마트폰까지, 하드웨어 백엔드 12개 이상(XNNPACK/QNN/CoreML 등).
  • 기존의 "PyTorch → ONNX → TFLite" 우회 없이 torch.export로 직행 — 자율주행 R&D처럼 PyTorch 중심 파이프라인이면 특히 자연스러움.
  • 아직 성숙 중이라 일부 op 미지원 → 여기서 처음으로 "export가 깨지는 경험"을 하게 되는데, 이것이 2단계(Transformer 양자화 지옥)의 예고편.
보드 없이 실기기 성능까지: Qualcomm AI Hub
모델을 업로드하면 클라우드에 물려 있는 실제 단말에서 컴파일·프로파일링·정확도 검증을 해줌. QNN 트랙(4단계)의 "HTP 실행은 보드 필요" 항목을 보드 구매 없이 상당 부분 대체 가능 — 0단계 표의 AI Hub 언급이 바로 이것.
사다리의 요점 — Lv.1~4는 전부 합쳐도 2~3주면 끝납니다. 이 과정에서 변환 → 양자화 → 배포 → fallback이라는 동일한 뼈대를 낮은 난이도에서 4번 반복하게 되고, 그 다음에 본 커리큘럼(1~5단계)으로 들어가면 "처음 보는 개념"이 거의 없는 상태가 됩니다. 이미 TensorRT/ONNX 경험이 있다면 Lv.1~2는 건너뛰고 Lv.3부터 시작해도 됩니다.

1단계 — 양자화 이론 1~2주

손으로 유도할 수 있어야 하는 것

q = round(x / s) + z      # s: scale, z: zero-point
x̂ = s * (q - z)           # dequant
  • symmetric vs asymmetric / per-tensor vs per-channel
    → weight는 per-channel symmetric, activation은 per-tensor asymmetric. 왜 그런지 설명 못 하면 면접에서 걸립니다.
  • QDQ 그래프: Q-DQ 노드 쌍이 박힌 ONNX. 요즘 모든 툴체인의 공용어.
  • 캘리브레이션: MinMax / Percentile(99.9%) / Entropy(KL) / MSE
  • QAT: fake quant + STE — round의 gradient를 어떻게 통과시키는가

읽을 것 (3개면 충분)

실습

ResNet18 → ONNX → INT8 PTQ (MinMax / Entropy 각각)
→ ImageNet-val 1000장 top-1 비교
→ 레이어별 SNR / 코사인 유사도 → "어느 레이어가 범인인지" 특정

2단계 — Transformer 양자화 지옥 2~3주 · 핵심

CNN 양자화는 거의 풀린 문제입니다. 이 JD가 사람을 못 구하는 이유는 Transformer 때문입니다.

왜 Transformer가 INT8에서 깨지는가

문제원인대응
LayerNorm채널별 activation outlier가 극심 → per-tensor scale이 outlier에 끌려감SmoothQuant, per-channel, FP16 유지
Softmax출력이 [0,1]에 몰림, exp가 dynamic range 폭발보통 INT8 금지 → FP16 fallback
GELU음수 구간 비선형 → INT8 정보 손실LUT 근사 또는 ReLU/HardSwish 교체
QKT / SV matmulactivation×activation 곱 (weight×activation이 아님) → 양쪽 다 dynamic별도 캘리브레이션, 종종 FP16

읽을 것

BEV / Occupancy 특유의 지뢰

  • grid_sample — BEV 뷰 변환의 핵심 op. TIDL에서는 grid가 경계를 벗어날 때 값이 틀어지는 알려진 버그가 있을 만큼 지원이 불안정하고, NPU에서는 아예 미지원인 경우가 많음.
  • Deformable Attention (BEVFormer의 심장) — 대부분의 임베디드 툴체인에서 커스텀 플러그인을 직접 작성해야 함. TensorRT plugin(C++/CUDA) 작성 경험이 이 직무의 강력한 차별점.
  • scatter / gather / dynamic shape — voxelization·pooling에 필수인데 NPU가 극도로 싫어함.
  • TIDL은 self-attention 블록이 있는 QDQ 모델이 컴파일 단계에서 에러를 내는 사례가 릴리스 노트에 올라올 정도. 즉 "Transformer + 자동차 NPU"는 아직 진행형 문제이고, 그래서 이 자리를 뽑는 것.

실습

DETR (또는 BEVFormer-tiny) → ONNX export 시도
→ 100% 실패 → 실패 로그 전부 기록
→ 하나씩 해결: op 치환, shape 고정, deformable attn 분해
→ INT8 PTQ → mAP 폭락 확인 → mixed precision으로 회복

3단계 — TensorRT로 첫 완주 2~3주

Orin이 있다면 여기서 시작하는 게 현실적. 다른 SoC도 개념은 90% 동일합니다.

배울 것

4단계 — 멀티 SoC 확장 3~4주

같은 ONNX 하나를 4개 백엔드에 밀어넣습니다. JD의 "multi-target deployment pipeline"이 정확히 이것.

TI TIDL

git clone https://github.com/TexasInstruments/edgeai-tidl-tools
# Docker → x86 컴파일 → host emulation 추론
  • 8-bit / 16-bit / mixed precision 지원. 8-bit 우선 → 정확도 갭 보이면 mixed 또는 16-bit로 상향.
  • PTQ 실패 시 → QAT 또는 pre-quantized(QDQ ONNX / TFLite)를 넣어 TIDL 캘리브레이션 단계를 우회.
  • 핵심: 어떤 레이어가 TIDL에 offload되고 어떤 게 ARM CPU로 fallback되는지 로그에서 읽어내기. fallback이 많으면 subgraph가 잘게 쪼개지고 성능이 무너짐.

Qualcomm QNN

from onnxruntime.quantization.execution_providers.qnn import (
    get_qnn_qdq_config, qnn_preprocess_model
)
  • HTP 백엔드는 양자화된 모델만 실행. FP32는 반드시 8/16-bit 정수로 먼저 양자화.
  • QNN EP는 ONNX op의 부분집합만 지원 (Loop, If 미지원). 양자화 유틸은 x86_64에서만 동작.
  • context binary(사전 컴파일된 그래프 캐시) 개념 → 초기화 시간 최적화 논의 가능.

Renesas DRP-AI

git clone https://github.com/renesas-rz/rzv_drp-ai_tvm
python3 compile_onnx_model_quant.py model.onnx -o out \
    -t $SDK -d $TRANSLATOR -c $QUANTIZER --images ./calib/
  • RZ/V2H의 DRP-AI MAC은 INT8 연산만 수행 → translation 전에 반드시 양자화.
  • DRP-AI는 feed-forward 전용 — RNN/LSTM/GRU 등 루프/재귀 구조 매핑 불가. DRP-AI3 양자화는 모든 노드 입력이 각자의 initializer를 가질 것을 요구. ← 이런 게 바로 design rules에 들어갈 항목
  • DRP-AI TVM은 TVM 기반이라 미지원 레이어를 CPU에 위임 → CPU 위임이 늘수록 느려짐 (TIDL과 동일 구조의 문제).
  • 캘리브레이션 이미지의 전처리(mean/std)를 학습 때와 정확히 일치시키지 않으면 정확도가 조용히 무너짐. 실무 최다 실수.
이 단계의 진짜 교훈
4개를 다 해보면 "툴체인은 달라도 문제는 똑같다"는 걸 체득하게 됩니다.

ONNX 표준 op → 벤더 지원 부분집합 → 그 중 INT8 가능한 부분집합 → 나머지는 CPU fallback → fallback 최소화가 전부

이 문장을 자기 경험으로 말할 수 있으면 면접은 통과입니다.
