2단계 BEVFormer-tiny — 실측 검증 보고서

fundamentalvision/BEVFormer(멀티뷰 카메라 → BEV 3D 검출)의 bevformer_tiny를 실제 RTX 3080에서 완주했다. 정본 venv로는 mmdet3d/mmcv가 안 돌아 레거시 venv를 따로 세웠고(무컴파일 — 프리빌트 휠), 검증을 2-tier로 나눴다: Tier A = grid_sample/MSDeformAttn op 지뢰를 정본 venv에서 격리 재현, Tier B = 실 mmcv op + BEVFormer-tiny 실모델(FP32 nuScenes-mini mAP + 전체 모델 export 벽). op 단정 반전 0건(초안이 맞았다) — 대신 실전 함정 2개(mmcv 커스텀 op은 CPU에서만 유효 export, 전체 export는 grid_sample이 아니라 lidar2img 사영에서 먼저 죽음)를 실측으로 채집했다.

§2 — 환경·스택 (2-tier, 실측)

BEVFormer 실모델은 정본 venv(torch 2.11)에서 안 돈다(mmcv-full 1.x/mmdet3d는 torch ≤1.13 전제). 그래서 op 검증(Tier A)은 정본에서, 실모델(Tier B)은 레거시에서.

Tier A — 정본 venv ~/emb-aiUbuntu 22.04 · RTX 3080 · driver 595.84 · CUDA 12.8 · torch 2.11.0+cu128 · onnx 1.18.0(IR 11) · onnxruntime-gpu 1.23.2 · TensorRT 10.16.1.11
Tier B — 레거시 venv ~/bevf-legacypython 3.10 · torch 1.13.1+cu117 · mmcv-full 1.7.0(프리빌트 cu117/torch1.13 휠) · mmdet3d 1.0.0rc6 · mmdet 2.28.2 · numpy 1.23.5 · numba 0.58.1 · onnx 1.14.1 · onnxruntime 1.16.3
무컴파일 (hard-won) "레거시 mmcv = 옛 CUDA 툴킷 재설치"는 통념이다. 실제로는 프리빌트 휠(download.openmmlab.com/mmcv/dist/cu117/torch1.13)이 있어 CUDA 소스 빌드를 전부 우회했고, torch 1.13+cu117이 드라이버 하위호환으로 CUDA 12.8 머신에서 그대로 CUDA init 됐다(정본 툴킷은 12.8뿐, 11.7 없음). mmdet3d는 --no-build-isolation + numba/opencv/numpy 핀 고정으로 설치, BEVFormer plugin의 dd3d/detectron2 체인은 4파일 패치로 우회(bevformer_tiny엔 dd3d 불필요).

§3 — Tier A: grid_sample / MSDeformAttn op 지뢰 5종

§4.6이 가르치는 단정은 대부분 개별 op의 export 거동이다. BEVFormer 전체·nuScenes 없이 정본 venv에서 최소 repro로 격리해 밟았다(b01~b05). 전부 실측, 초안 반전 0건.

§4 — Tier B: 실제 mmcv MSDeformAttn op (B1·B2)

Tier A는 순수 PyTorch 폴백을 옮겨 밟은 것. Tier B는 레거시 venv의 진짜 mmcv 커스텀 op(MultiScaleDeformableAttention)을 직접 돌리고 export했다(b06).

B1 · 확인 레거시 mmcv CUDA op은 컴파일 없이 CUDA 12.8에서 산다

프리빌트 mmcv-full 1.7.0 _ext(.so) 로드 성공 → MultiScaleDeformableAttnFunction(진짜 CUDA 커널) 실행, 순수 PyTorch 분해와 |Δ|max=1.4e-6 일치. 드라이버 하위호환으로 정본 머신에서 바로 돈다.

B2 · 함정 실제 모듈 export는 디바이스에 따라 갈린다 — CUDA=조용히 틀린 그래프

바닐라 mmcv엔 symbolic도 is_in_onnx_export 가드도 없고 forward가 value.is_cuda로 분기한다. 그래서 export 디바이스가 그래프를 가른다.

export 디바이스결과노드그래프 입력판정
CPU표준 op 분해244 (GridSample 4)[query, value, reference_points]✅ 유효
CUDAexit0 · checker PASS4 (Constant1,MatMul1,Add2)[query] 만🔴 silent-wrong
design rule symbolic 없는 autograd.Function을 트레이서가 표현 못 해 MSDeformAttn 출력 전체를 Constant로 baked → value·reference_points가 그래프 입력에서 사라진다. 모델이 입력을 무시하는데 에러 없이 통과한다. → mmcv 커스텀 op 모델은 반드시 CPU 텐서로 export하고, 직후 그래프 입력 목록으로 value/reference_points 생존을 검증하라. 커스텀 op ONNX 노드 경로는 DerryHub/BEVFormer_tensorrt 포크가 추가하는 것이지 바닐라 mmcv엔 없다.

b 전체 모델 export는 grid_sample이 아니라 point_sampling에서 먼저 죽는다

바닐라 BEVFormer엔 ONNX export 스크립트가 아예 없다(tools/에 onnx/deploy/pth2onnx 전무). "전체를 그냥 torch.onnx.export"(CPU 강제) 하면 CPU forward는 성공(bev_embed (2500,1,256))하지만 export는 즉시:

b09_fullmodel_export_attempt.py — RuntimeError
RuntimeError: shape '[1, 6, 6, 1, 4, 4]' is invalid for input of size 96
  at encoder.py:119  # point_sampling (BEV→카메라 사영)
    lidar2img = lidar2img.view(1, B, num_cam, 1, 4, 4)   # B가 트레이서에서 6으로 오바인딩

왜 "지옥"인가 — 3층 BEVFormer export가 험한 진짜 이유는 grid_sample 하나가 아니다. ① img_metas(lidar2img 사영·can_bus)가 forward 내부 기하의 입력이라 그래프에서 사라지면 안 되는데 비텐서 dict→numpy로 들어와 트레이서와 충돌(위 실측). ② forward_test가 self.prev_frame_info['prev_bev']로 시간축 재귀(stateful) — 프레임 간 상태라 단일 그래프 트레이스 불가. ③ 그 안쪽에 §3~4의 grid_sample/MSDeformAttn 지뢰. 포크의 export 래퍼는 정확히 이 셋을 걷어낸다 — lidar2img·can_bus·prev_bev를 명시적 텐서 입력으로 승격 + point_sampling 재작성 + 커스텀 op 플러그인. 바닐라를 그대로 내보내는 유효 경로는 없다.

c · 정직한 한계 전체 모델 INT8 mAP은 범위 밖

(b)로 유효한 전체 모델 ONNX가 안 나오므로 INT8 PTQ→INT8 mAP는 도달 불가. 포크의 커스텀 op 플러그인 툴체인(TRT 8.5/CUDA 11.6 기준 → 정본 TRT 10.16/CUDA 12.8에 재빌드 필요)이 전제. op 단위 양자화 거동은 §3~4가 실 mmcv op로 이미 검증했다.
