8단계 · 캡스톤 · BEVDet end-to-end 실측 (walking skeleton)

BEVDet 캡스톤 — 커스텀 CUDA op을 sudo 없이 관통시키다

794줄 초안(미검증)을 실제 AI-LAP RTX 3080에서 관통시켰다. 벽은 문서가 예고한 곳이 아니었다 — BEVDet의 bev_pool_v2 커스텀 CUDA op은 torch≤1.13+CUDA≤11.7을 요구하는데 이 머신의 유일 toolkit은 CUDA 12.8이라, 문서 §3이 준 2안(Docker cu116 / blackwell 패치)이 둘 다 불가했다. 이 보고서는 그 벽을 user-space cu117 툴체인(제3의 길)으로 넘어 nuScenes-mini에서 FP32 파이프라인을 walking skeleton(문서 §9 완주 기준)으로 관통시킨 기록이다. 절대 정확도는 정직한 폴백(Baidu-locked). TRT-plugin INT8은 후속 세션에서 관통 — 지연 사다리·엔진 크기·출력편차는 INT8 관통 전용 보고서.

§1 — 실행 요약

한 줄 요약

BEVDet 캡스톤의 진짜 관문은 양자화가 아니라 "레거시 커스텀 CUDA op을 최신 드라이버 머신에서 빌드하는 것"이었다. Docker도 sudo도 없이 — nvcc·libcudart·Python.h 세 조각을 user-space에 조달하고 CUDA_HOME을 손으로 조립해 bev_pool_v2를 컴파일(9.13 MB .so), nuScenes-mini에서 export→CUDA op(GPU 실행)→eval 하네스를 exit 0으로 관통시켰다(walking skeleton 완주). FP32 forward p50 34.06 ms는 공식 README의 33.3 ms(RTX 3090)와 근접해 실연산을 교차확증한다.

  • 헤드라인 (제3의 길, §3): 문서 §3의 Docker cu116·blackwell 패치가 둘 다 막힌 머신에서, micromamba cuda-nvcc=11.7(V11.7.99) + pip nvidia-cuda-runtime-cu11(실제 libcudart.so.11.0) + micromamba python 헤더로 CUDA_HOME을 조립 → torch._check_cuda_version의 MAJOR 불일치 hard-error를 우회하고 커스텀 CUDA op 빌드. 정본 emb-ai venv 오염 0(격리 legacy env).
  • 두 번째 벽 (spconv): 카메라 전용 BEVDet인데 bundled mmdet3d detectors/__init__.py가 LiDAR-fusion 검출기(DAL)를 eager import → spconv 필요. 6개 __init__ 다중패치보다 spconv-cu117 설치가 깨끗.
  • walking skeleton 완주 (§4): mini info pkl 생성(323 train/81 val, 태그 bevdetv3—초안 v2 아님)→FP32 eval 하네스가 exit 0으로 관통. bev_pool_v2 CUDA op이 GPU에서 실제 실행(view_transformer.py의 LSS 경로 확인).
  • 정직한 폴백 (§4·§6): BEVDet-R50 정식 가중치는 Baidu Pan 전용(헤드리스 접근 불가). init 가중치(torchvision backbone + 랜덤 head)라 mAP 0.0000은 예상값(버그 아님) — 파이프라인은 완결, 절대 정확도만 가중치 대기. TRT-8.5-plugin INT8은 후속 세션에서 관통(INT8 보고서) — 단 지연·크기·출력편차만 유효(절대 정확도는 여전히 가중치 대기).

§3 — 커스텀 CUDA op 컴파일: 제3의 길 (핵심)

BEVDet의 bev_pool_v2(LSS pooling)는 python fallback이 없는 커스텀 CUDA 커널이다. 빌드하려면 nvcc가 필요한데:

벽 — torch MAJOR CUDA 불일치 (hard-error)

torch 1.13.1은 cu117로 빌드됐고, 이 머신의 유일 nvcc는 CUDA 12.8. torch.utils.cpp_extension._check_cuda_version가 컴파일러 MAJOR(12) ≠ torch build MAJOR(11)에서 RuntimeError로 중단한다(minor 불일치는 warning, MAJOR는 hard-error). §4.6 BEVFormer와 동일한 근본원인 — 레거시 mmcv/mmdet3d 커스텀 커널은 torch≤1.13+CUDA≤11.7에 묶여 있다.

문서 §3 초안이 준 길은 (a) Docker nvcr.io … cu116 또는 (b) blackwell 패치뿐. 이 머신엔 Docker 없음, 정본 venv 오염 불가 → 둘 다 막힘.

해법 — user-space cu117 툴체인 조립 (sudo·Docker·4.3GB runfile 전부 회피)

커스텀 CUDA op을 빌드하는 데 필요한 세 조각을 각각 user-space에 조달하고 CUDA_HOME을 손으로 조립한다:

조각출처왜 이걸로
nvccmicromamba cuda-nvcc=11.7 → V11.7.99완전한 프론트엔드. pip nvidia-cuda-nvcc-cu11은 ptxas만 있어 불충분
libcudartpip nvidia-cuda-runtime-cu11==11.7.99실제 libcudart.so.11.0. torch 번들 libcudart-<hash>.so는 -lcudart 링크 불가
Python.hmicromamba python=3.10 → CPATHpython3.10-dev 미설치·sudo 불요 우회
CUDA_HOME~/capstone-bev/cuda-home 조립bin/include/nvvm→cu117, lib64에 libcudart.so→pip 런타임
# 빌드 env — 핵심은 -lcudart가 실제 SONAME libcudart.so.11.0으로 해결되게 하는 것
export CUDA_HOME=~/capstone-bev/cuda-home
export PATH=$CUDA_HOME/bin:$PATH
export TORCH_CUDA_ARCH_LIST=8.6            # RTX 3080 sm_86
export CPATH=~/capstone-bev/pyhdr/include/python3.10
cd ~/capstone-bev/BEVDet
nvcc --version                           # → release 11.7, V11.7.99
python setup.py build_ext --inplace
# 산출: bev_pool_v2_ext.*.so  9,131,040 bytes  (forward/backward export)

두 번째 벽 — spconv (카메라 전용인데 LiDAR-fusion을 eager import)

모델 빌드 시 ModuleNotFoundError: No module named 'spconv'. 원인: bundled mmdet3d models/detectors/__init__.py가 모든 검출기를 eager import → 그중 DAL(LiDAR-camera fusion)이 spconv 요구. spconv 의존이 detectors/middle_encoders/roi_heads/ops 6곳 캐스케이드. → 6개 __init__ 다중패치보다 pip install spconv-cu117(2.3.6 + cumm 0.4.11)가 깨끗.

설계규칙: OpenMMLab detectors __init__은 eager-import-all — 쓰지도 않는 모달리티의 의존까지 끌고 온다. 누락 의존은 "이 모델이 그걸 쓴다"가 아니라 "패키지가 그걸 import한다"는 신호. 설치가 패치보다 싸다.

§4 — 데이터 · FP32 walking skeleton

문서 §9의 완주 기준은 "먼저 BEVDet FP16(여기선 FP32)을 dGPU에서 끝까지 관통 = walking skeleton". 그 관문을 실제로 통과시킨다.

walking skeleton — 무엇이 진짜고 무엇이 랜덤인가

파이프라인은 끝까지 실행된다(모든 블록 exit 0). 단 가중치는 backbone만 진짜(ImageNet 사전학습)고 나머지는 랜덤(정식 가중치 Baidu-locked). 아래가 그 구조:

무엇이 검증됐고, 무엇이 안 됐나 (정직)

검증됨: 툴체인·데이터·커스텀 CUDA op(GPU 실행)·eval 하네스의 기능적 완결성(파이프라인이 끝까지 돈다).

안 됨: 절대 mAP/NDS 문헌대조(공개 BEVDet-R50 ≈ mAP 0.298/NDS 0.379). BEVDet-R50 정식 가중치는 Baidu Pan 전용(헤드리스 접근 불가, WebSearch 2회로 미러 못 찾음) → 사용자 사전승인 fall-back 지점. 가중치 확보 시 동일 하네스로 재실행하면 절대 정확도가 채워진다.

§5 — 지연 교차확증 (가중치와 무관하게 유효)

정확도는 가중치에 의존하지만 latency는 forward 계산 그래프에만 의존한다 — 랜덤 head라도 실연산량은 정식 모델과 동일. FP32 forward 지연(batch1, CUDA event-timed, N=30)을 공식 README와 대조:

FP32 latency (batch1, event-timed, N=30)값
p5034.06 ms
mean / min / max34.18 / 33.91 / 35.55 ms
재실행 p50 (지터 확인)34.29 ms (지터 내 일치)
peak GPU mem420.9 MiB
params44.25 M
공식 README BEVDet-R50 total (RTX 3090)33.3 ms

실측 34.06 ms(3080)가 공식 33.3 ms(3090)와 근접 — 3080이 3090보다 소폭 느린 것과도 정합. latency는 실연산을 교차확증하므로 가중치 미확보와 무관하게 유효하다.

§6 — 판정 · 산출물

판정 1 — walking skeleton 완주 (문서 §9 기준 충족)

커스텀 CUDA op 빌드→데이터→export→GPU 추론→eval 하네스가 끝까지 관통. 문서 §9의 완주 기준("먼저 끝까지 관통 = walking skeleton, 4-target all-success는 보너스")을 충족한다.

판정 2 — 제3의 길이 문서 §3의 빈칸을 채운다

문서 §3은 Docker cu116·blackwell 패치 2안만 준다. Docker 없고 sudo 없는 머신에서도 user-space cu117 툴체인 조립으로 레거시 커스텀 CUDA op을 빌드할 수 있음을 실증 — 이 경로가 §3의 제3의 선택지로 문서에 삽입됐다.

판정 3 — 절대 정확도는 폴백, INT8/TRT-plugin은 후속 세션 관통

절대 mAP/NDS: BEVDet-R50 정식 가중치 Baidu-locked → 파이프라인은 완결이나 절대 정확도는 여전히 가중치 대기. INT8/TRT-plugin: §4-4 경로 A1(BEVDet --int8 TRT8.x)이 요구하던 TRT 8.5 + 커스텀 TRTBEVPoolv2 플러그인 툴체인을 후속 세션에서 user-space에 실제 조립해 관통(W1~W6) → FP32→FP16→INT8 지연 사다리(14.68→4.91→2.63ms)·엔진 크기·출력편차 실측. 전체 서술은 INT8 관통 전용 보고서. 단 init 가중치라 지연·크기·오차전파만 유효(절대 정확도 아님). 이 머신의 INT8 축은 3·5단계(ResNet50)·4단계(HTP)에 이어 여기서도 완결.
