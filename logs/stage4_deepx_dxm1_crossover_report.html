DEEPX DX-M1 — host-bound ↔ NPU-bound 크로스오버

직전 벤치(지연·처리량·전력)의 헤드라인은 "천장은 DX-M1이 아니라 Pi 5의 PCIe Gen2×1"(host-bound)이었다 — yolo26n은 코어를 늘려도 처리량이 평평했고, 온보드 프로파일러가 D2H 출력전송 21.8ms ≫ 연산 8.86ms를 보였다. 이 축은 그 캐비앗 #3("host-bound은 Pi 5 탓이지 DX-M1 천장이 아님")을 반대 사례로 닫는다: 같은 DX-M1·같은 Pi 5·같은 dxrun/dxbenchmark에서 모델만 바꿔 — 출력이 700× 작은 resnet50(같은 정확도 축의 native .dxnn 재사용)을 올리면 NPU 연산이 실제 천장이 되어 3코어 2.19× near-linear 스케일이 부활한다. 세 번째 모델 YOLOV5S로 변수를 격리한다: 연산이 resnet50보다 더 가벼운데도 출력이 크면 D2H-bound로 남는다 → regime을 정하는 건 연산이 아니라 출력(D2H) 크기.

§1 — 실행 요약

같은 DX-M1(3코어 @1000MHz)·같은 Pi 5에서 세 모델의 코어 스케일링(1→3코어 처리량 비)과 온보드 프로파일러 스테이지 분해(연산 vs D2H)를 나란히 측정. 유일한 변수는 모델 = 출력 텐서 크기.

헤드라인 천장은 하드웨어가 아니라 모델이 정한다. 직전 벤치의 "host-bound(코어 스케일 1.00)"은 DX-M1의 보편 성질이 아니라 yolo26n(큰 출력)의 성질이었다. 출력이 작은 resnet50에선 D2H가 무시가능(0.11ms)해져 NPU 연산(2.77ms)이 실제 병목이 되고, 3코어가 2.19× near-linear 스케일한다. 코어 잡 분포가 결정적 증거 — resnet50은 961/910/1010(3코어 균등), yolo26n은 472/28/2(코어 1·2 굶김): 공유 PCIe Gen2×1 D2H 링크가 한 코어치 출력만으로 포화돼 나머지 코어를 못 먹인다.

§2 — 환경·방법

호스트 / NPURaspberry Pi 5 (Cortex-A76 ×4, 8GB, Debian 13) + DEEPX DX-M1 (M.2, 3코어 @1000MHz) · PCIe Gen2 X1 (dxrt-cli -s 확인)
런타임 / 도구DXRT v3.4.2+d803450 · dxrun(지연·처리량) · dxbenchmark(프로파일러 → profiler.json)
모델 (prebuilt .dxnn)resnet50_native([1,224,224,3] uint8 → [1,1000] f32, 정확도 축 재사용) · yolo26n([1,640,640,3] → 6-head) · YOLOV5S_1([1,512,512,3] → 3-head, dx_rt 예제)
지연 (seq)dxrun -m M.dxnn -s -t 5 -w 1 — 단일 스트림, "FPS" = 1/지연
처리량 (async)dxrun -m M.dxnn -b -n <코어> --buffer-count 8 -t 5 -w 1 — 파이프라인 최대 처리량
프로파일러dxbenchmark --dir . -t 5 --warmup 1 → cwd에 profiler.json(잡·스테이지별 start/end ns) → analyze_profiler.py
방법 정밀화 -n은 코어 개수가 아니라 코어 ID다. dxrun/dxbenchmark --help: 0=NPU_ALL · 1=NPU_0 · 2=NPU_1 · 3=NPU_2 · 4=NPU_0/1 · 5=NPU_1/2 · 6=NPU_0/2. 따라서 이 리포트의 코어-카운트 스윕은 1코어=-n 1(NPU_0) · 2코어=-n 4(NPU_0/1) · 3코어=-n 0(NPU_ALL)로 매핑한다. 직전 벤치의 "async 1/2/3-core=91.5 평평" 축은 실은 세 개별 단일코어(NPU_0/1/2)가 각각 91.5였던 것 — 결론(host-bound)은 동일하되, 이번엔 진짜 코어-카운트 곡선(1→2→3코어 누적)으로 재확증한다. --buffer-count 8은 버퍼 부족 혼입 방지(§5 참조: bc=2면 resnet50조차 641로 굶음).
교차확증 dxrun async 3코어 ≈ dxbenchmark 프로파일러 내부 파이프라인 fps(독립 도구·독립 측정): resnet50 1078.93 ≈ 1071.49 · yolo26n 91.19 ≈ 90.86 · YOLOV5S 41.01 ≈ 40.91. 두 도구가 3모델 모두 일치 → 처리량 수치 신뢰.

§3 — 코어 스케일링 크로스오버 (헤드라인)

코어를 1→2→3개로 늘렸을 때 처리량 배율. NPU 연산이 병목이면 코어가 늘수록 처리량↑(이상 3.0×), 공유 D2H 링크가 병목이면 코어를 늘려도 평평(1.0×).

코어 스케일링 배율 (3코어 처리량 / 1코어 처리량)

초록=NPU-compute-bound(스케일함) · 빨강/노랑=D2H-bound(평평) · 세로선 1.0×(스케일 없음)·2.0×·3.0×(이상)

모델seq (1스트림)1코어2코어3코어3c/1cregime

단위 fps(async 처리량, --buffer-count 8). ResNet50은 1→2코어 1.75× → 3코어 2.19×로 누적 스케일(3코어에서 ~1080 근처 H2D/호스트-피드 천장에 접근해 살짝 sublinear). 두 YOLO는 모든 단계에서 평평 — 코어 1개가 이미 공유 D2H 링크를 포화시켜 2·3코어가 아무것도 더 못 함.

§4 — 프로파일러 스테이지 분해 (범인 확정)

dxbenchmark 온보드 프로파일러(NPU_ALL)의 스테이지별 p50(ms). 어느 스테이지가 지배하느냐가 regime을 정한다.

모델H2D연산(Inference)D2H병목비코어 잡 분포
ResNet500.712.770.11연산 25.3× D2H961 / 910 / 1010 (균등)
yolo26n3.489.0021.81D2H 2.4× 연산472 / 28 / 2 (굶김)
YOLOV5S3.322.5921.14D2H 8.2× 연산295 / 7 (굶김)
범인 = D2H (PCIe Gen2×1), 모델 출력이 방아쇠 ResNet50: 출력 [1,1000] = 4,000 B → D2H 0.11ms(무시가능), 연산 2.77ms가 25배 지배 → compute-bound. 3코어가 각자 연산하고 tiny 출력을 순식간에 뱉으니 3코어 균등(961/910/1010).
yolo26n: 출력 2,822,400 B(706×) → D2H 21.81ms(199×)가 연산 9.0ms를 2.4배 지배 → D2H-bound. 공유 PCIe가 직렬화돼 코어 1·2가 28/2로 굶음.
스테이지 자체는 모델 무관(같은 링크·같은 NPU). 바뀐 건 출력 텐서 크기 하나뿐 — 그게 D2H 시간을 정하고, D2H가 병목 여부를 정하고, 병목이 코어 스케일 가능 여부를 정한다.

§5 — 변수 격리 (YOLOV5S · buffer-count)

"compute가 무거워서 resnet50이 스케일한 것 아닌가?"를 반증한다. YOLOV5S는 세 모델 중 연산이 가장 가볍다(2.59ms < resnet50 2.77ms). 그런데도 출력이 가장 크므로(5.48MB) D2H-bound로 남고, 3코어 처리량이 resnet50의 1/26이다.

3코어 처리량 vs 출력 크기 (연산은 반대 방향)

세로선 250·500·1000 fps · YOLOV5S는 연산 최경량인데 출력 최대 → 최저 처리량

buffer-count 대조 실험 — 파이프라인 버퍼를 늘리면 NPU에 여유가 있는 모델만 처리량이 오른다(NPU_ALL):

모델bc=2bc=4bc=8bc=16해석
ResNet50641.351108.341086.391079.08bc2→4서 641→1108 급등 (NPU 여유 있음, 버퍼가 굶겼던 것)
yolo26n52.3085.4791.1991.1791서 포화 (물리적 D2H 벽, 버퍼로 못 넘음)
변수 격리 결론 regime을 정하는 건 연산량이 아니라 출력(D2H) 크기다. resnet50(연산 2.77ms + 출력 4KB)은 compute-bound라 코어·버퍼가 먹히고, YOLOV5S(연산 2.59ms + 출력 5.48MB)는 더 가벼운 연산인데도 D2H-bound라 26× 느리다. DX-M1의 3코어를 살리려면 출력을 작게(분류 헤드·경량 후처리 온-NPU·낮은 해상도) 하거나 PCIe 대역을 넓혀야(네이티브 Gen3×4) 한다.
