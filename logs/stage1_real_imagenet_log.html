1라벨 매핑 — 한 출처만 믿지 않는다

val 아카이브에는 라벨이 없다. devkit의 meta.mat(ILSVRC2012_ID→WNID)과 ILSVRC2012_validation_ground_truth.txt로 만들고, 독립 출처인 Caffe val.txt와 대조했다.

devkit 유도 매핑 ↔ Caffe val.txt 교차검증
val_synset_map.txt  : 50,000 줄 (devkit meta.mat + ground_truth 유도)
caffe val.txt       : 50,000 줄 (독립 출처)
불일치              : 0 / 50,000  → 0건, 두 출처 완전 일치 ✅
클래스 수           : 1000
클래스별 장수       : min=50 max=50  → 전부 50장 ✅
정렬 WNID 규약      : 0건 위반 → torchvision 0-based 규약 일치 ✅
여기서 틀리면 전부 무의미라벨 인덱스 규약이 어긋나면 top-1이 조용히 낮게 나오고, 그걸 양자화 손실로 오독한다. torchvision 규약은 정렬한 WNID의 0-based 순번이다. 두 출처가 50,000건 전부 일치했고, 정렬 규약 위반도 0건이었다.

3전처리 uint8 캐시 — 며칠을 96분으로

모델 13종 × 50,000장을 반복 평가한다. JPEG 디코딩이 병목이라 매번 디코딩하면 CPU에 묶인다. decode→resize→crop 직후의 uint8을 저장하면 이후엔 /255·정규화만 남아 GPU 바운드가 된다. PIL resize/crop 출력이 uint8이므로 이 지점까지는 비트 무손실이다.

$ python3 prep_cache.py # 8 프로세스, 2분 36초
squash .npy  shape=(50000, 224, 224, 3) dtype=uint8  7.01 GiB
tv     .npy  shape=(50000, 224, 224, 3) dtype=uint8  7.01 GiB
names.txt   : 50,000 줄   labels.npy: (50000,) int16
squash  표본 24장 max|캐시-직접| = 0.000e+00  → 비트 동일 ✅
tv      표본 24장 max|캐시-직접| = 0.000e+00  → 비트 동일 ✅
두 가지 전처리를 나란히 굽는다squash = 문서의 preprocess(종횡비 무시 256×256 resize), tv = torchvision 표준(짧은변 256 bilinear + center crop 224). 문서의 절대값이 공개값보다 낮았던 원인을 이 둘의 차이로 분리하려는 것이다.
