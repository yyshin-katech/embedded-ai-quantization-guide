8단계 · 캡스톤 · BEVDet INT8/TRT 관통 (후속 세션)

BEVDet INT8 — 커스텀 TRT 플러그인 6벽을 넘어 실 엔진 사다리로

FP32 walking skeleton(1차 보고서)이 "다음 과제"로 남긴 INT8/TRT-plugin을 후속 세션에서 관통시켰다. 문서 §4-4 경로 A1(convert_bevdet_to_TRT.py --int8)은 bev_pool_v2 커스텀 TensorRT 8.5 플러그인을 직접 빌드해야 하는 벽 — 이를 6개 벽(W1~W6)을 차례로 넘어 통과하고, FP32→FP16→INT8 TRT 엔진 3종을 빌드해 지연 사다리·엔진 크기·FP32 대비 출력편차를 실측했다. init 가중치라 절대 정확도는 여전히 폴백 — 유효 산출물은 가중치와 무관한 지연·크기·오차전파.

§1 — 실행 요약

한 줄 요약

BEVDet INT8의 벽은 양자화 알고리즘이 아니라 "커스텀 op을 TensorRT 8.5 플러그인으로 빌드·export·엔진화하는 툴체인"이었다. 풀 mmdeploy CMake 없이 bevpoolv2 2개 TU만 직접 컴파일(W3), torch 1.13 트레이서가 죽는 지점을 export 전용 shim으로 우회(W5), deprecated build_engine segfault를 build_serialized_network로 교체(W6) → FP32/FP16/INT8 엔진 3종 빌드. INT8은 FP32 대비 지연 ×5.58 / 엔진 ×5.24 축소, FP32 대비 출력 corr 0.985~1.000.

  • 6벽 관통 (§2): W1 TRT 8.5.3.1 · W2 cuDNN 8.6 · W3 플러그인 직접 빌드(libmmdeploy_tensorrt_ops.so 58,896 B, TRTBEVPoolV2Creator 등록) · W4 pycuda cu117 · W5 export shim · W6 build API. 각 벽의 증상·해법은 capstone_constraints.md 벽 5.
  • W5 = 진짜 export 벽 (§3): torch.onnx.export 추적 중 nested QuickCumsumCuda(symbolic 없는 CUDA autograd.Function)에서 RuntimeError: _Map_base::at + segfault. TRTBEVPoolv2.forward를 shape-only new_zeros shim으로 갈아끼우면 symbolic만 mmdeploy::bev_pool_v2 노드를 emit하고 실연산은 추론 시 플러그인이 수행 → 엔진 정확도 무영향(표준 mmdeploy 기법).
  • W6 = 벽이 아니었다 (§4): convert의 from_onnx가 쓰는 deprecated builder.build_engine가 TRT 8.5.3에서 segfault. 플러그인 탓이 아니라 API 탓 — build_serialized_network로 바꾸니 플러그인 레이어 포함 완전 빌드. INT8 캘리브는 ENTROPY_2·mini 81장.
  • 지연 사다리 (§5): FP32 14.68 → FP16 4.91(×2.99) → INT8 2.63 ms(×5.58 vs FP32, ×1.87 vs FP16), batch1 event-timed. TRT FP32 엔진(14.68ms)은 PyTorch eager(34.06ms)보다 2.3× 빠름 — 교차확증.
  • 캐비앗 (§6·§7): init 가중치 → 절대 mAP≈0(무의미). 유효한 건 가중치-무관 지연·엔진 크기·FP32대비 출력 corr/rel_max. INT8 출력편차는 height head corr 0.985가 최저, dim head rel_max 0.218이 최대 — 양자화 오차 전파를 보여준다.

§2 — 6벽 사다리 (W1 → W6)

1차 세션은 "INT8은 TRT 8.5 + 커스텀 플러그인 툴체인 필요 → 다음 과제"로 폴백했다. 후속 세션은 그 툴체인을 user-space에 실제로 조립해 경로 A1을 끝까지 통과시켰다. 6벽 중 진짜 새 벽은 W3·W5이고, W6은 벽처럼 보였으나 deprecated API 문제였다.

벽내용 → 해법
W1TensorRT 8.5.3.1 (pip 휠) — legacy env 설치
W2cuDNN 8.6 (libcudnn.so.8) 런타임
W3mmdeploy fork bevpoolv2 플러그인 빌드 — 풀 CMake 트리 우회. 2개 TU(trt_bev_pool_kernel.cu + trt_bev_pool.cpp)가 self-contained → cu117 nvcc(-arch=sm_86 -std=c++14) + g++(-std=c++17) 직접 컴파일·링크(-lnvinfer -l:libcudart.so.11.0) → libmmdeploy_tensorrt_ops.so 58,896 B, mmdeploy::TRTBEVPoolV2Creator(bev_pool_v2 v1) 등록
W4pycuda user-space cu117 빌드 (convert/bench 요구)
W5ONNX export 트레이서 사망 — nested QuickCumsumCuda에서 _Map_base::at + segfault → forward를 export 전용 shim으로 (§3)
W6엔진 빌드 segfault — deprecated build_engine → build_serialized_network (§4). 벽 아님(API)

W3 — 커스텀 플러그인을 풀 CMake 없이 빌드

mmdeploy 전체 빌드 트리(수십 op·의존)를 세우는 대신, 필요한 op의 TU만 직접 컴파일했다. bevpoolv2는 커널 .cu와 플러그인 .cpp 2개로 self-contained라 nvcc·g++ 직접 호출로 충분하다. 레시피 → scripts/build_trt_plugin.sh.

# W3: bevpoolv2 TRT 플러그인 직접 빌드 (핵심 3스텝)
# [1] nvcc: 커널 → kernel.o (sm_86, c++14, fPIC)
$NVCC -c trt_bev_pool_kernel.cu -o kernel.o -arch=sm_86 -std=c++14 -Xcompiler -fPIC -I$TRT85/include ...
# [2] g++: 플러그인 → plugin.o (c++17)
g++ -c trt_bev_pool.cpp -o plugin.o -fPIC -std=c++17 -O2 -I$TRT85/include ...
# [3] link → libmmdeploy_tensorrt_ops.so (MODULE)
g++ -shared kernel.o plugin.o -o libmmdeploy_tensorrt_ops.so \
  -L$TRT85/lib -lnvinfer -lnvinfer_plugin -l:libcudart.so.11.0 -l:libcublas.so.11 -l:libcudnn.so.8
# → 58,896 B, nm -D: T mmdeploy::TRTBEVPoolV2Creator (bev_pool_v2 v1)

§3 — export shim (W5, 진짜 export 벽)

torch.onnx.export가 TRTBEVPoolv2.forward를 추적하는 순간 죽었다. 원인은 forward가 내부에서 호출하는 QuickCumsumCuda — symbolic이 없는 CUDA autograd.Function이라, torch 1.13 JIT 트레이서가 이를 그래프 노드로 기록하려다 내부 std::map::at에서 RuntimeError: _Map_base::at를 던지고 segfault한다.

해법 — forward를 shape-only shim으로 (export/inference 분리)

TRTBEVPoolv2는 이미 symbolic(→ g.op('mmdeploy::bev_pool_v2', ...))을 가지고 있다. export 동안엔 forward의 실제 CUDA 연산이 필요 없다 — 트레이서는 출력 shape만 알면 되고, 그래프 노드는 symbolic이 emit한다. 그래서 forward를 올바른 shape의 new_zeros로 갈아끼우면 트레이서가 죽지 않고, 실연산은 추론 시 TRT 플러그인이 수행한다. 이것이 표준 mmdeploy custom-op export 기법이다.

# W5: export 전용 shim (실연산 대신 shape-correct zeros)
def _export_shim_forward(g, depth, feat, ranks_depth, ranks_feat, ranks_bev,
                         interval_starts, interval_lengths, out_height=128, out_width=128):
    feat = feat.unsqueeze(0); depth = depth.unsqueeze(0)
    out_shape = (depth.shape[0], out_height, out_width, feat.shape[-1])
    return feat.new_zeros(out_shape)   # 실 CUDA op 미실행 → 트레이서 안 죽음
bp.TRTBEVPoolv2.forward = staticmethod(_export_shim_forward)
# symbolic은 그대로 mmdeploy::bev_pool_v2 노드 emit → onnx 176.9 MB, checker PASS

결과 trtbevdet.onnx = 176,901,052 B (opset 11), mmdeploy::bev_pool_v2 노드 포함. 실연산은 엔진 추론 시 W3에서 빌드한 플러그인이 담당하므로 엔진 정확도에 영향 없음.

§4 — build API (W6) + INT8 캘리브

export가 뚫린 뒤, convert의 from_onnx가 엔진 빌드에서 segfault했다. 처음엔 플러그인의 build-time autotuning 문제로 의심했으나, VERBOSE 빌드로 확인하니 deprecated builder.build_engine(network, config)가 TRT 8.5.3에서 이 네트워크에 대해 죽는 것이었다. 모던 builder.build_serialized_network(network, config)로 바꾸니 플러그인 레이어 포함 전체 엔진이 완전 빌드됐다.

# W6: deprecated build_engine → build_serialized_network
# engine = builder.build_engine(network, config)      # segfault (TRT 8.5.3, deprecated)
serialized = builder.build_serialized_network(network, config)   # 완전 빌드
open(out + '.engine', 'wb').write(bytes(serialized))
# 종료 시 pycuda+TRT teardown 순서 segfault(무해) → os._exit(0)로 exit code 청소

알고리즘 ENTROPY_CALIBRATION_2 · 표본 nuScenes-mini val 81장(create_calib_input_data가 img는 per-sample, ranks/metas 인덱스는 sample-0 재사용 → 플러그인 enqueue OOB 없음) · 배치당 ~0.15s. INT32 인덱스 텐서(interval_starts/lengths 등)는 Missing scale and zero-point 경고 = 양자화 안 함(정상). FP16 서브노멀 경고(114+49 weights)도 무해.

§5 — 지연 사다리 (batch1, CUDA event-timed)

세 엔진을 같은 입력(nuScenes-mini 첫 샘플: 6-cam img + 5 ranks)으로 execute_v2, 15 warmup + 60 iter CUDA-event 측정. 정확도는 가중치에 의존하지만 지연은 계산 그래프에만 의존 — 랜덤 head라도 실연산량은 정식과 동일.

교차확증 — TRT FP32 엔진 vs PyTorch eager

같은 RTX 3080에서 TRT FP32 엔진 14.68 ms는 1차 보고서의 PyTorch eager forward 34.06 ms보다 2.3× 빠르다 — 커널 퓨전·파이썬 오버헤드 제거. 두 값 모두 같은 계산 그래프(랜덤 head 포함)이므로, TRT 최적화의 순수 효과를 격리한다.

§6 — 출력편차 (양자화 오차 전파)

절대 예측은 무의미하지만, FP32 엔진 출력 대비 FP16·INT8 출력의 편차는 가중치와 무관하게 "양자화가 각 head에 얼마나 오차를 주입하나"를 보여준다. 6개 detection head 출력(reg·height·dim·rot·vel·heatmap)의 상대오차(rel_max)를 INT8에서 측정:

headINT8 rel_maxINT8 corrFP16 corr
output_0 reg0.06920.999540.99998
output_1 height0.09470.985280.99948
output_2 dim0.21840.999340.99998
output_3 rot0.19870.999861.00000
output_4 vel0.07110.999740.99999
output_5 heatmap0.10810.999821.00000

FP16은 전 head가 FP32와 거의 동일(corr ≥0.9994, rel_max ≤0.010). INT8은 height head(corr 0.985)가 상관 최저, dim head(rel_max 0.218)가 상대오차 최대 — 정식 가중치라면 이 head들이 양자화에 가장 민감할 후보다(민감도 분석 §4-5의 실측 진입점).

§7 — 판정 · 산출물

판정 1 — 경로 A1(BEVDet 공식 스크립트) INT8 관통

문서 §4-4 경로 A1(convert_bevdet_to_TRT.py --int8)을 실제로 통과. 1차 보고서가 "다음 과제"로 남긴 TRT-8.5-plugin INT8을, 커스텀 플러그인을 user-space에 직접 빌드(W3)하고 export shim(W5)·build API(W6)로 우회해 FP32/FP16/INT8 엔진 3종을 실측 사다리로 만들었다.

판정 2 — 진짜 벽은 W3·W5, W6은 벽이 아니었다

W3(플러그인을 풀 CMake 없이 2 TU 직접 빌드)와 W5(트레이서 _Map_base::at → export shim)가 새 지식. W6은 플러그인 문제로 보였으나 deprecated build_engine의 segfault였다 — build_serialized_network로 즉시 해소. "플러그인 탓" 가설을 먼저 배제하라는 설계규칙.

판정 3 — 절대 정확도는 여전히 폴백, 상대만 유효

init 가중치(torchvision backbone + 랜덤 head) → 절대 mAP≈0. 이번 산출물의 유효 범위는 가중치-무관 지연 사다리·엔진 크기·FP32대비 출력편차. mini 81장 캘리브라 INT8 스케일도 소표본. Baidu 정식 가중치 확보 시 동일 하네스로 정확도까지 재실행 가능. 지연은 event-timed·batch1·forward-only라 3·5단계 ResNet50 사다리와 절대 1:1 비교 불가(모델·해상도 상이), 구조·상대만.
