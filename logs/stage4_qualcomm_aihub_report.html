4단계 · 멀티 SoC · Qualcomm 벤더 NPU 실측 (클라우드 실기기)

Qualcomm AI Hub — Hexagon HTP 실측 검증 보고서

CPU 폴백 프록시(Raspberry Pi 5)가 준 것은 offload 0%의 바닥값이었다. 이 보고서는 그 위 — 벤더 NPU가 실제로 얼마나 빠른가(on-device latency)와 얼마나 많이 가속기로 올라가는가(NPU offload%) — 를 보드 없이 Qualcomm AI Hub 클라우드의 실기기(QCS8550 프록시 · SA8775P ADP 자동차 보드)에서 ResNet50으로 실측한다. 산출물은 3·5단계 자산과 동일한 INT8 QDQ / FP32 ONNX.

§1 — 실행 요약

한 줄 요약

같은 ResNet50을 Qualcomm AI Hub로 실제 Snapdragon Hexagon HTP 두 종(QCS8550 프록시 · SA8775P 자동차 ADP)에 컴파일·프로파일하니 — 두 디바이스 모두 100% NPU offload(폴백 0), INT8이 FP32(HTP에선 fp16) 대비 ×1.77(QCS8550) · ×2.03(SA8775P) 빨랐다. 이는 CPU 프록시가 못 준 벤더-NPU 실측 지연 + offload%다. 단, on-device INT8 정확도에서 조용한 함정을 발견했다(§4).

  • 지연·offload (신뢰): compile/profile은 그래프 구조를 충실히 보존 → 두 디바이스 100% offload, INT8 배속 ×1.77·×2.03. execution_cycles로 교차 확증(FP32 4.68M/6.19M vs INT8 3.75M/4.46M).
  • 정확도 함정 (silent-wrong): ORT가 만든 외부 INT8 QDQ ONNX를 HTP로 임포트하면 on-device top-1이 0.75→0.005로 조용히 붕괴. 같은 경로의 FP32(fp16)는 충실(0.745, ORT와 96% 일치) → 입력경로·전처리·파싱은 정상이고, 범인은 "외부 QDQ scale을 HTP 임포트가 존중하지 않음". 올바른 경로 = AI Hub 자체 quantize job(§4).
  • 툴체인 발견 3종 (§5): ① AI Hub 프론트엔드가 ORT/TRT보다 엄격 — logits가 value_info+IO 양쪽인 ONNX를 거부(컴파일 실패) ② FP32 ONNX도 HTP에선 fp16으로 실행(native fp32 없음) ③ 입력 인터페이스는 엄격 NCHW — NHWC 피드 거부(레이아웃 가설 기각).
  • 정직한 범위: AI Hub는 Qualcomm 전용이므로 이 실측은 §06 세 벤더 중 Qualcomm 축만 채운다. TI(TDA4VM)·Renesas(RZ/V2H)는 보드/툴체인 대기.

§3 — 지연 · NPU offload (핵심 실측, 신뢰)

compile→profile은 그래프를 충실히 보존한다(정확도 함정과 무관). 두 디바이스, 두 정밀도의 on-device 추정 지연·컴퓨트유닛 분배·실행 사이클:

디바이스 · 정밀도on-device 지연INT8 배속NPU offloadexecution_cycles레이어
QCS8550 · FP32 (→HTP fp16)1864 µs—125/125 (100%)4,677,822125
QCS8550 · INT8 QDQ1052 µs×1.77128/128 (100%)3,754,903128
SA8775P ADP · FP32 (→HTP fp16)3056 µs—125/125 (100%)6,192,577125
SA8775P ADP · INT8 QDQ1505 µs×2.03128/128 (100%)4,462,570128

읽는 법 — 이게 왜 CPU 프록시보다 위인가

4단계 CPU 폴백 프록시(Raspberry Pi 5)는 "모든 op가 CPU로 떨어졌을 때"의 offload 0% 바닥값이었다. 여기서는 offload 100% — ResNet50의 모든 노드가 Hexagon HTP로 올라갔다. §06의 목표("Offloaded ≈ Total, subgraph 최소")를 벤더 실기기에서 정량 달성한 그림이다. INT8 배속(×1.77·×2.03)은 HTP의 INT8 전용 MAC이 fp16 대비 이기는, NPU의 존재 이유를 직접 보여준다.

§4 — on-device 정확도 진단: 외부 QDQ의 조용한 붕괴 (silent-wrong)

지연·offload가 좋다고 수치가 맞는다는 뜻은 아니다. QCS8550에서 200장(ImageNet val 서브셋)으로 on-device 예측을 ORT-CPU·정답과 대조했다:

경로 (QCS8550, 200장)on-device top-1ORT-CPU 대비ORT 일치율distinct 클래스
ORT-CPU (기준)0.750——181
FP32 (→HTP fp16)0.745−0.005 (충실)0.96183
INT8 · 외부 ORT-QDQ0.005붕괴0.00535
INT8 · AI Hub 자체 quantize0.735−0.015 (회복)0.94184

20장 대조군도 동일: FP32 0.75 / INT8-외부 0.0 → 스케일 무관한 구조적 붕괴. FP32가 충실하다는 것은 입력(NCHW)·전처리·업로드·출력파싱·정확도 하네스가 모두 정상이라는 뜻 — 붕괴는 외부 QDQ 임포트 특유다.

범인 = 외부 QDQ scale을 HTP 임포트가 존중하지 않음

ORT 양자화기가 만든 이 INT8 QDQ ONNX는 scale이 정상이다 — 동일 자산이 4단계 CPU 프록시의 x86 CPUEP에선 top-1 0.753(1,000장, cpu_proxy/…__x86_cpu__int8.json). 같은 ONNX를 AI Hub가 QNN context binary로 컴파일하면 그래프는 돌지만(100% offload) on-device 수치가 0.005로 붕괴한다 — 예측이 35개 클래스에 집중(409/862/818/506/723). exit 0·정상 shape 출력이라 조용하다. 권장 경로는 외부 QDQ 지참이 아니라 AI Hub 자체 submit_quantize_job(HTP-native QDQ 생성). 아래 카드가 그 대조다.

올바른 경로 대조 — AI Hub 자체 quantize로 0.735 회복 (게다가 더 빠름)

동일 200장에서 AI Hub의 submit_quantize_job(HTP-native INT8 QDQ)은 top-1 0.735 · ORT 일치 0.94 · distinct 184 — FP32(fp16) 0.745·ORT-CPU 0.750에 근접 회복한다. 외부 QDQ의 0.005 붕괴가 임포트 특유였음을 확정하는 대조군이다.

부수 실측: native-quant는 정확할 뿐 아니라 더 leaner — 748 µs · 1,985,339 cyc · 127층(100% NPU)로, 외부-QDQ INT8(1052 µs·3,754,903 cyc·128층)보다 빠르다. HTP-native 양자화가 더 최적화된 그래프를 만든다(외부 QDQ는 임포트만 될 뿐 최적 스케줄이 아님).

잡: quantize jp1jz48kp → compile jgnnv69vg → profile jpyx314r5 → inference jglxmv0eg.

§5 — 툴체인 발견 3종

1AI Hub 프론트엔드는 ORT/TRT보다 엄격 — value_info↔IO 충돌 거부

ORT 양자화기가 shape-inference로 넣은 logits가 graph.value_info와 graph.output에 동시에 존재(ONNX 스펙 위반). ORT·TensorRT는 관대해 통과시키지만 AI Hub 컴파일은 실패한다:

# 원본 INT8 QDQ 컴파일 (jp2wyk06p)
❌ FAILED  Tensors {'logits'} occur in value_info but also in model IO.

# 수정: IO와 충돌하는 value_info 제거 (계산 그래프 불변)
io = set(i.name for i in g.input) | set(o.name for o in g.output)
g.value_info = [v for v in g.value_info if v.name not in io]  # 122 → 121
onnx.checker.check_model(m)   # PASS
# 정리본 컴파일 (jglxmv22g) → SUCCESS, 100% offload

→ clean_valueinfo_for_aihub.py. 다른 툴체인에서 통과하던 QDQ ONNX라도 AI Hub行 검증을 한 번 더 거쳐야 한다.

2FP32 ONNX도 HTP에선 fp16으로 실행 (native fp32 없음)

HTP는 fp16/int8 네이티브다. FP32 모델을 올리면 그래프 첫머리에 자동 변환 노드가 삽입된다 — 프로파일 execution_detail에서 실측:

# profile execution_detail[1]
{'name': 'QNN_DATATYPE_FLOAT_32_converted_input_QNN_DATATYPE_FLOAT_16',
 'compute_unit': 'NPU', 'execution_cycles': 35758}

→ 이 보고서의 "FP32" 행은 엄밀히는 fp16-on-HTP다. 그래서 FP32 정확도도 ORT-CPU(진짜 fp32)와 완전 동일이 아니라 0.745(−0.005)다.

3입력 인터페이스는 엄격 NCHW — NHWC 가설 기각

붕괴(§4)의 첫 가설은 "HTP가 channel-last를 기대한다(NHWC)"였다. 두 경로로 반증:

# 컴파일 잡의 선언 입력
job.target_shapes = {'input': ((1, 3, 224, 224), 'float32')}   # NCHW

# NHWC (1,224,224,3) 피드 시도 (jgj7nve1g)
❌ FAILED  Cannot assign data from unexpected shape.
           Expected [1, 3, 224, 224], got [1, 224, 224, 3].

→ AI Hub는 선언된 NCHW를 엄격 검증한다. 내 NCHW 피드가 올바른 형상이었고, 붕괴 원인은 레이아웃이 아니라 §4의 외부-QDQ 임포트다.

§6 — 판정 · 캐비앗 · 산출물

판정 4종

  • ① 벤더-NPU 지연·offload 확보: QCS8550 ×1.77 · SA8775P ×2.03, 둘 다 100% offload. CPU 프록시(offload 0%)가 못 준 "가속기가 이겨야 할 최소선" 위의 실측.
  • ② 외부 QDQ = on-device 정확도 함정: compile/profile은 통과해도 on-device INT8 수치가 조용히 붕괴(0.005). FP32(fp16)는 충실(0.745). 지연이 좋다고 수치를 믿지 말 것.
  • ③ 올바른 INT8 경로 = AI Hub 자체 quantize: top-1 0.735 · ORT 일치 0.94로 FP32(fp16) 0.745에 근접 회복(외부 QDQ 0.005 붕괴와 대조). 게다가 748µs·1.99M cyc로 외부-QDQ INT8(1052µs)보다 빠름 — HTP-native 양자화가 더 leaner한 그래프를 만든다.
  • ④ 정직한 범위: Qualcomm 축만 실측. TI·Renesas는 보드/툴체인 대기.

캐비앗 (절대값 비교 금지, 상대 관계만)

  • 절대 지연은 on-device estimated_inference_time(HTP 스케줄러 추정)이며 배치1 기준 — 다른 단계의 wall-clock/event-timed와 1:1 비교 불가.
  • top-1은 200장 서브셋이라 부풀림 가능(1단계 함정 0). 상대 관계(FP32 충실 vs INT8 붕괴)만 유효.
  • "QCS8550 (Proxy)"는 프록시 디바이스, "SA8775P ADP"는 실제 자동차 보드 — 절대속도 비교보다 각 디바이스 내 INT8/FP32 관계가 논점.
  • FP32는 실제로 fp16-on-HTP(§5-2). "FP32 대비 배속"은 "fp16 대비 int8 배속"으로 읽어야 정확.
