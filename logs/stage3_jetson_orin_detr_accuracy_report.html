DETR 정확도유효 INT8 — case-C 우회 후 온디바이스 COCO mAP

앞선 Orin DETR 보고서(커밋 9ef2a58)는 트랜스포머의 지연을 실측했지만, explicit-QDQ INT8이 stage3 case C(shiftIsAllZeros)로 파싱조차 안 돼 DETR INT8 정확도는 측정하지 못했다. 이 후속은 그 빈칸을 닫는다 — 먼저 대칭 재양자화로 case C(+B)를 우회하고, 그 과정에서 드러난 트랜스포머 고유의 두 번째 벽(self-attention의 quantized-constant를 빌더가 거부)을 op_types_to_quantize=[Conv,Gemm]로 넘어, 정확도유효 INT8 엔진을 처음으로 빌드한다. 그리고 COCO val 1000장에서 pycocotools mAP를 FP32/FP16/explicit-sym/implicit 4엔진으로 실측한다.

과제(메모리 verbatim): "DETR 대칭 재양자화 → case-C 우회 → explicit INT8 정확도유효 엔진 · on-board COCO mAP." 네 발견 모두 같은 1000장·같은 800×1066 전처리 위 상대 관계로 읽는다.

발견 1 · 대칭 재양자화가 case C를 우회 → explicit INT8이 빌드된다stage2 detr_int8.onnx(zp≠0 1085/1485 + INT32 bias DQ 149)는 trtexec 직접 파서에서 node 0에 죽었다(shiftIsAllZeros). ResNet50이 빌드됐던 바로 그 레시피 — ActivationSymmetric+WeightSymmetric(zp=0 → C 해소)·QuantizeBias=False(INT32 bias DQ 제거 → B 해소)·backbone conv1 제외(case D) — 로 detr_int8_sym.onnx(43.4 MB, zp_nonzero=0·int32_bias_DQ=0) 생성 → 9ef2a58에서 build-failed였던 explicit INT8이 빌드된다(44.69 MiB·11.002 ms).
발견 2 · 트랜스포머 고유의 두 번째 벽 — quantized-constant-in-attention대칭 우회 후에도 ORT 기본 op 커버리지(모든 op 양자화: Reshape/Transpose/Softmax/Mul/MatMul/Where/Constant…)로는 파싱은 통과하나 빌더가 거부: qdqGraphOptimizer::matchQuantizedConstantPluginOrDQ … Quantized constant is only allowed before DQ or PLUGIN. op_types_to_quantize=[Conv,Gemm](가중치 보유 op만; attention matmul·LayerNorm·Softmax는 FP16 유지)로 넘는다 — 이는 stage2 §4.5("op 선택 mixed는 mAP를 거의 못 움직인다, 레버는 activation 입도")와 정확히 일치.
발견 3 · case-C 픽스는 툴체인 언락이지 정확도 구제가 아니다 (헤드라인)정확도유효 엔진은 stage2 폭락을 재현: FP32 0.4237 → INT8 0.2383(−43.8%), 작은 객체 mAP_s 0.2179 → 0.0336(−84.6%). stage2(ORT-QDQ·dynamic·CUDA·5000장)는 0.4207 → 0.2402(−42.9%)·mAP_s −77% — 다른 두 경로가 같은 폭락에 착지 → 교차확증. 레버는 sym/case-C 픽스가 아니라 activation 양자화 입도(SmoothQuant, stage2 §4.4가 per-tensor 격차의 59.9% 회복).
발견 4 · implicit --int8(0.4073)은 더 나은 INT8이 아니다 — 정확도가 nominaltrtexec --int8은 캘리브 캐시 없이 빌드돼 [W] Calibrator is not being used. Users must provide dynamic range …를 찍는다 → 데이터 기반 activation 레인지가 없다. 그래도 INT8 커널은 돈다(implicit이 FP16보다 빠르고 9.43<13.28 ms·엔진도 작다 58.76<81.43 MiB → INT8 활성, 순수 FP16 폴백이 아님) — 단 무통제(비-데이터) 레인지 위에서다. 그래서 정확도는 미주장: 여기선 우연히 FP16 근처(0.4073, −3.9%)에 착지했지만 짝인 ResNet50-DLA implicit는 같은 무통제 경로에서 0.017로 붕괴. 정확도를 걸 수 있는 건 explicit·캘리브된 QDQ뿐.
CAVEAT 절대 mAP는 stage2와 비교 불가 — fixed 800×1066 강제 리사이즈(종횡비 왜곡) vs stage2 dynamic shape, TRT vs ORT, 1000 vs 5000장. 상대 FP32→INT8 폭락만 결과이고, 그 상대 폭락이 stage2를 교차확증한다. 1000장 서브셋(1단계 함정 0: 서브셋 mAP도 부풀려짐)·같은 번들 상대 델타만. int8_implicit(0.4073)은 무통제 자동 레인지라 정확도 미주장. Jetson은 NVIDIA edge이지 세 자동차 벤더(TI/Qualcomm/Renesas) 아님.

헤드라인 대칭 재양자화는 explicit INT8을 빌드 가능하게 만들었지만(9ef2a58 build-failed → 빌드됨), accuracy-valid 엔진은 stage2 폭락을 재현한다 — 0.4237 → 0.2383(−43.8%), mAP_s −84.6%. 다른 경로(TRT·fixed·1000)와 stage2(ORT·dynamic·5000, −42.9%·mAP_s −77%)가 같은 폭락에 착지하니 결과는 견고하다. case-C 픽스는 툴체인 언락이지 정확도 구제가 아니다 — 레버는 activation 입도(SmoothQuant, stage2 §4.4).
부수 · 발산 지표는 약한 프록시 FP32 대비 raw 발산: FP16 logits_corr 0.99991/boxes_corr 0.99944(거의 동일), sym 0.98236/0.94532, implicit 0.98038/0.94062. sym과 implicit의 전역 corr이 거의 같은데(0.982 vs 0.980) mAP는 0.17 벌어진다 — 100×92 logits 전역 Pearson corr은 no-object logit 차원이 지배해 약한 프록시다. pycocotools mAP가 권위 지표.

읽는 법 지연 순서 implicit(9.43) < sym(11.00) < FP16(13.28) < FP32(25.85). sym이 implicit보다 느린 건 sym은 Conv+Gemm만 INT8(결정적 QDQ 배치)이고 implicit은 무통제 레인지로 더 많은 층을 INT8로 깔기 때문 — 단 implicit의 그 속도는 정확도 미주장과 맞바꾼 것이다(§4). 바로 이 "FP16보다 빠름"이 implicit이 순수 FP16 폴백이 아님을 증명한다(INT8 커널이 실제로 돎). 엔진 크기도 sym(44.69) < implicit(58.76) < FP16(81.43).

§6 — 판정·산출물

YES 대칭 재양자화로 case C(+B)와 attention 빌더 벽을 넘어 정확도유효 explicit INT8 엔진을 빌드했다

9ef2a58에서 build-failed였던 gpu_int8_explicit가 detr_int8_sym.onnx(zp_nonzero=0·int32_bias_DQ=0) + op_types_to_quantize=[Conv,Gemm]로 빌드된다(44.69 MiB·11.002 ms). 툴체인 언락 달성.

NO 그러나 case-C 픽스는 정확도를 구제하지 않는다 — DETR INT8은 여전히 폭락한다

accuracy-valid mAP 0.4237 → 0.2383(−43.8%), mAP_s −84.6%. stage2(−42.9%·mAP_s −77%)를 다른 경로에서 재현. 레버는 op 선택/대칭 여부가 아니라 activation 양자화 입도(SmoothQuant, stage2 §4.4).

CAVEAT implicit --int8(0.4073)은 정확도 미주장 — 캘리브 없음 → 무통제 레인지

TRT 로그 Calibrator is not being used가 직접 증거. INT8 커널은 돌지만(FP16보다 빠름=순수 FP16 폴백 아님) 레인지가 데이터 기반이 아니라 정확도를 걸 수 없다 — 여기선 FP16 근처(0.4073)지만 짝인 ResNet50-DLA implicit는 0.017 붕괴. 무통제 경로는 어느 방향으로든 정확도를 보장하지 못한다.
