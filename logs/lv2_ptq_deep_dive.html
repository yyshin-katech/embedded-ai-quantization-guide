lv2_convert.py
# 0) 예시 모델 (실제로는 학습된 모델을 로드). MNIST용 소형 CNN.
model = tf.keras.Sequential([
    tf.keras.layers.Input((28, 28, 1)),
    tf.keras.layers.Conv2D(8, 3, activation="relu"),
    tf.keras.layers.MaxPooling2D(),
    tf.keras.layers.Flatten(),
    tf.keras.layers.Dense(10),
])
# (학습 생략: 데모용. 실제로는 model.fit(...)으로 학습된 가중치 사용)

# 1) FP32 baseline
conv = tf.lite.TFLiteConverter.from_keras_model(model)
save("model_fp32.tflite", conv.convert())

# 2) Dynamic range PTQ — 플래그 하나. representative_dataset 불필요.
conv = tf.lite.TFLiteConverter.from_keras_model(model)
conv.optimizations = [tf.lite.Optimize.DEFAULT]              # 가중치만 INT8, activation은 동적
save("model_dynamic.tflite", conv.convert())

# 3) Float16 PTQ — GPU 친화. representative_dataset 불필요.
conv = tf.lite.TFLiteConverter.from_keras_model(model)
conv.optimizations = [tf.lite.Optimize.DEFAULT]
conv.target_spec.supported_types = [tf.float16]             # 가중치 FP16
save("model_fp16.tflite", conv.convert())

# 4) Full INT8 PTQ — representative_dataset로 activation 범위 캘리브레이션
calib_images = np.random.rand(200, 28, 28, 1).astype("float32")  # 데모용 랜덤

def representative_data_gen():
    for img in tf.data.Dataset.from_tensor_slices(calib_images).batch(1).take(200):
        yield [img]

conv = tf.lite.TFLiteConverter.from_keras_model(model)
conv.optimizations = [tf.lite.Optimize.DEFAULT]                       # 양자화 스위치 ON
conv.representative_dataset = representative_data_gen                  # 캘리브레이션 데이터
conv.target_spec.supported_ops = [tf.lite.OpsSet.TFLITE_BUILTINS_INT8]  # full-INT8 강제
conv.inference_input_type = tf.int8                                   # 입출력도 정수로
conv.inference_output_type = tf.int8
Note GPU 경고 2줄(cuda_executor/gpu_device)에 대한 사용자의 자체 진단("변환 작업 자체는 CPU로도 무관")은 정확합니다 — 왜 정확한지는 §4에서 이 프로젝트의 기존 cuDNN/TensorRT LD_LIBRARY_PATH 픽스와 대조해 설명합니다.

1PTQ 공통 이론 — Affine Quantization

4갈래 모두 결국 같은 수식 위에 있습니다. 무엇을 언제(변환 시점 vs 추론 시점) 양자화하느냐, 그리고 zero-point를 0으로 고정하느냐(symmetric)만 다릅니다.

이 4가지 변형은 전부 Post-Training Quantization(PTQ) — 학습이 끝난(혹은 이 데모처럼 학습을 생략한) 가중치를 재학습 없이 양자화하는 방식입니다. Nagel et al.(2021)의 정의를 빌리면, PTQ는 "재학습이나 라벨 데이터가 필요 없는, 가벼운 push-button 방식"이고, 그 대안인 Quantization-Aware Training(QAT)은 양자화 오차를 학습 루프에 넣어 정확도를 더 끌어올리지만 비용이 더 큽니다[4]. lv2_convert.py엔 model.fit(...)이 아예 없으므로 4개 전부 PTQ입니다.

균일 affine 양자화 (uniform affine quantization)

Jacob et al.(2018)이 제안한 스킴이 TFLite 정수 커널의 기반입니다[1]. 실수(real) 텐서 r을 정수(quantized) 텐서 q로 매핑할 때:

q = clip( round(r / S) + Z , q_min, q_max ) 역방향(역양자화): r ≈ S × (q − Z)　　S = scale (float32), Z = zero-point (int)

이 매핑의 핵심은 — r ≈ S(q−Z)를 행렬곱에 대입해 정리하면, float 곱셈이 int32 누산기(accumulator) 위의 정수 곱셈-누적 + 마지막 한 번의 rescale로 바뀐다는 것입니다. 이게 바로 "정수 전용 하드웨어에서 더 빨리 돈다"는 말의 실체입니다[1].

구분Zero-point보통 어디에왜
SymmetricZ = 0가중치(weight)정수곱에 zero-point 교차항이 안 붙어 계산이 단순 — Jacob et al.[1]
AsymmetricZ ≠ 0활성화(activation)ReLU 뒤 값 분포가 0 근처로 치우쳐 있어 비대칭 범위가 정밀도를 아낌 — Gholami et al.[3]

또 하나의 축은 스케일을 어느 단위로 따로 두느냐입니다. Krishnamoorthi(2018)의 핵심 결론이 바로 이 부분인데 — 가중치는 채널별(per-channel), 활성화는 레이어별(per-layer)로 8비트 양자화하면 다양한 CNN 구조에서 float 대비 정확도 손실이 2% 이내로 좁혀진다는 것입니다[2]. per-tensor(레이어 전체가 스케일 하나) 방식은 채널 간 가중치 스케일 편차가 큰 레이어(대표적으로 depthwise conv)에서 정밀도를 크게 잃습니다.

예시 1 · 실측값으로 본 affine 양자화

이론이 아니라 이 실습에서 실제로 나온 model_int8.tflite를 인터프리터로 열어 직접 읾은 값입니다:

입력 텐서:  scale=0.0039216, zero_point=-128   (float [0,1] → int8 [-128,127])
출력 텐서:  scale=0.0073905, zero_point=-18    (미학습 Dense(10) 로짓, 비대칭)
가중치(Dense, per-channel, axis=0, 10개 채널): scale[0..3]=[0.00052183, 0.00052120, 0.00052192, 0.00052207] · zero_point=0 (전부)

왜 입력 scale이 정확히 1/255에 가까운가: representative_dataset이 np.random.rand(...)(균등분포 [0,1))라서 캘리브레이션이 찾은 min≈0, max≈1 → S=(1−0)/255=0.0039216, Z=−128(실수 0.0이 정수 −128에 정확히 대응). 이미지 입력을 8비트로 양자화할 때 나오는 정석적인 값입니다.

왕복 오차 확인 — 실수 r=0.2를 위 scale/zero-point로 왕복시키면:

q = round(0.2 / 0.0039216) + (−128) = round(51.0) − 128 = −77 r' = 0.0039216 × (−77 − (−128)) = 0.0039216 × 51 = 0.199999... 절대오차 ≈ 7×10⁻⁷ — round-to-nearest의 최대 오차 한계는 이론상 S/2 ≈ 0.00196

가중치는 왜 채널마다 scale이 다른가(per-channel) — 위 4개 scale이 서로 미세하게 다른 게 바로 Krishnamoorthi(2018)가 말한 per-channel 양자화의 실체입니다[2]. 채널 0의 가중치 w=0.01을 그 채널 scale(0.00052183)로 양자화하면 q=round(0.01/0.00052183)=19 → 역양자화 19×0.00052183=0.0099148(오차 8.5×10⁻⁵) — zero_point가 전부 0인 것도 이론과 일치(가중치=symmetric).

흥미로운 교차검증: model_dynamic.tflite의 이 Dense 레이어 per-channel scale은 model_int8.tflite와 완전히 동일합니다. 두 방식 모두 가중치 양자화는 representative_dataset과 무관하게 가중치 텐서 자체의 min/max에서만 계산되기 때문 — 두 변형의 차이는 활성화를 언제 양자화하느냐뿐이라는 걸 실측으로 확인한 셈입니다(§2에서 계속).

24갈래 상세 — 뭘 언제 양자화하는가

공통 수식은 하나지만, 가중치/활성화 각각을 양자화하는지, 양자화 시점이 변환 시(static)인지 추론 시(dynamic)인지, 캘리브레이션 데이터가 필요한지가 네 갈래를 가릅니다.

0FP32 Baseline

양자화 없음 — 비교 기준선. 파일 크기·정확도·지연시간 모두 나머지 3개를 평가하는 분모 역할만 합니다.

가중치만 staticDynamic-range 양자화

conv.optimizations = [tf.lite.Optimize.DEFAULT] 한 줄. 공식 문서는 이 방식을 이렇게 설명합니다: "활성화는 항상 float로 저장되고, 양자화된 커널을 지원하는 연산에서는 처리 직전에 8비트로 동적으로 양자화되고 처리 후 다시 float로 역양자화된다"[5]. 즉:

  • 가중치 — 변환 시점에 정적으로 int8 양자화 (§1의 per-channel scale이 그 결과)
  • 활성화 — 그래프 메타데이터엔 float로 남아있고, 매 추론마다 해당 연산 바로 앞에서 그 배치의 min/max를 보고 즉석 양자화 → 정수 커널 실행 → 다시 float로 역양자화("hybrid kernel")
  • representative_dataset 불필요 — 활성화 범위를 미리 알 필요가 없으니까

실측 근거: model_dynamic.tflite를 인터프리터로 열면 입력/출력 텐서의 quantization 튜플이 (0.0, 0)으로 나옵니다 — 그래프 I/O가 여전히 float32라는 직접 증거입니다(§1 참고).

Tip 크기 4x, 속도는 왜 2-3x뿐인가 — 가중치만 정수라 activation quantize/dequantize 오버헤드가 매 연산마다 붙기 때문. Krishnamoorthi(2018)는 일반 CPU에서 2-3x, 고정소수점 SIMD가 있는 전용 프로세서에서는 최대 10x까지 관측했다고 보고합니다[2].

가중치만, 16비트Float16 양자화

conv.target_spec.supported_types = [tf.float16]만 추가. 가중치를 32비트 float가 아니라 16비트 float로 저장 — 정수 변환이 아니라 부동소수점 정밀도만 반토막내는 방식입니다. 공식 문서: "GPU 같은 일부 하드웨어는 이 축소 정밀도 연산을 네이티브로 수행할 수 있다"[6]. 뒤집어 말하면 CPU에는 그 네이티브 fp16 커널이 없는 경우가 많아, 첫 추론 전에 가중치를 다시 fp32로 업샘플링합니다 — 저장 공간은 아끼지만 CPU 연산량은 그대로라는 뜻입니다.

  • representative_dataset 불필요 — 활성화를 건드리지 않으니까
  • 목표: GPU delegate(네이티브 fp16 연산)와 짝을 이룰 때 진짜 이득. CPU 단독이면 크기만 절반
실측과 이론의 교차검증 이번 실습은 CPU 인터프리터로만 돌렸으므로(§4의 GPU 미탑재 경고 참고), fp16 모델이 CPU에서 fp32와 거의 같은 지연시간(0.011 vs 0.012ms)을 보인 것[§3]은 "CPU에선 연산량 이득이 없다"는 문서 설명과 정확히 들어맞습니다.

가중치+활성화 모두, staticFull-Integer(INT8) 양자화

4갈래 중 유일하게 representative_dataset이 필요합니다 — 활성화 범위를 실행 전에 알아야 정적 scale/zero-point를 정할 수 있기 때문입니다. target_spec.supported_ops = [TFLITE_BUILTINS_INT8]은 단순한 "선호"가 아니라 강제입니다 — 공식 문서: "양자화할 수 없는 연산이 있으면 컨버터가 에러를 던지도록 보장한다"[7]. 즉 dynamic-range처럼 지원 안 되는 연산을 조용히 float로 넘기는 게 아니라, 변환 자체가 실패합니다 — 이건 두 방식의 실행 철학이 다르다는 뜻이라 §5에서 다시 다룹니다.

확인된 표기 차이 · int8 vs uint8 공식 문서의 예제 코드는 converter.inference_input_type = tf.uint8를 씁니다[7]. 이번 실습 스크립트는 tf.int8을 명시했고, 로그의 input_inference_type: INT8이 정확히 그걸 반영합니다 — 오타나 실수가 아니라 둘 다 유효한 선택입니다. int8과 uint8은 zero-point가 정확히 128만큼 어긋난 같은 아핀 매핑의 다른 인코딩일 뿐입니다(uint8 = int8 + 128). 다만 Coral Edge TPU 컴파일러처럼 uint8 입력을 정해놓고 요구하는 특정 타깃이 있어, 문서 예제가 그쪽 관례를 따른 것으로 보입니다 — 이 특정 배경(왜 문서가 uint8을 기본값으로 골랐는지)까지는 이번 조사로 권위 있게 확인하지 못했습니다.

목표 하드웨어: 공식 문서는 "Edge TPU 같은 정수 전용 가속기가 요구", "저전력 마이크로컨트롤러가 작아진 모델·빨라진 추론의 수혜자"라고 명시합니다[7]. 이 실습에서 정수-only 배포가 가능한 건 이 변형 하나뿐입니다(§3 표의 마지막 열).

또 하나 눈에 띄는 점: dynamic-range(16,744 B)와 full-INT8(16,912 B)의 파일 크기가 거의 같습니다(차이 168 B, FP32의 0.29%). 이유는 구조적으로 다릅니다 — 가중치 양자화 자체는 §1에서 확인했듯 동일하고, full-INT8만 추가로 각 활성화 텐서의 scale/zero-point 메타데이터를 그래프에 박아 넣는데, 이 모델처럼 레이어가 몇 개뿐이면 그 메타데이터 부피가 무시할 수준이라는 뜻입니다. 레이어가 수백 개인 실제 모델이라면 이 차이가 더 벌어질 수 있습니다.

지연시간: 이론과 반대로 나온 이유

주목할 실측 결과 Full-INT8(0.020ms)이 4개 중 가장 느립니다 — "정수 양자화 = 더 빠름"이라는 통상적 기대와 정반대입니다. 원인을 이론으로 짚어보면 세 가지가 겹칩니다.
  1. 노이즈 바닥(noise floor) — lv2_bench.py는 time.perf_counter()로 감싼 단일 Python 루프 측정입니다. 값 전체가 0.009~0.020ms 구간에 몰려있는데, 이는 파이썬 인터프리터 디스패치·GIL·타이머 분해능 자체의 오버헤드와 같은 자릿수입니다. ladder_notes.md의 자체 관찰도 동일합니다: "이 정도로 작은 데모 모델·CPU에서는 추론시간 차이가 노이즈 수준".
  2. 연산량이 너무 작음(overhead-bound, not compute-bound) — Conv2D(8, 3×3) → MaxPool → Flatten → Dense(10)은 총 MAC(곱셈-누적) 수가 수천 단위입니다. Jacob et al.(2018)과 Krishnamoorthi(2018)가 보여준 정수 커널의 이득은 MobileNet급(수백만 MAC) 모델, 그리고 고정소수점 SIMD/dot-product 명령이 있는 하드웨어(ARM NEON, x86 VNNI 등)에서 두드러집니다[1][2]. 이 데모 크기에서는 quantize/dequantize glue 코드의 오버헤드가 정수 연산 자체의 이득을 상쇄하고도 남습니다.
  3. 구조적으로 처리할 게 더 많음 — full-INT8은 입력 양자화 → 정수 연산 → 출력 역양자화까지 매 호출마다 거치는 반면, dynamic-range는 활성화 캐스팅이 연산 내부에만 국한됩니다. 워크로드가 아주 작을 때는 이 추가 경계 처리 비용이 상대적으로 크게 보입니다.

따라서 이 표에서 뽑을 수 있는 결론은 "이 4개 중 어느 게 빠르다"가 아니라 — 양자화의 지연시간 이득은 모델 규모와 타깃 하드웨어에 조건부라는 것입니다. 실기기(MCU/NPU)나 더 큰 모델로 갈수록 이 격차는 이론이 예측하는 방향(정수 > float)으로 벌어지는 것이 정상입니다.

파이프라인 정합성 — argmax 일치 확인

lv2_infer.py — 핵심 로직
# INT8 모델이면 입력을 양자화 스케일로 정수화 (역양자화 공식의 역함수)
if inp["dtype"] == np.int8:
    scale, zp = inp["quantization"]
    x = np.round(x / scale + zp).astype(np.int8)
...
# 출력이 INT8이면 다시 float로 역양자화
if out["dtype"] == np.int8:
    oscale, ozp = out["quantization"]
    y = (y.astype(np.float32) - ozp) * oscale

4개 변형에 동일한 랜덤 입력을 흘리면 전부 argmax=8로 일치합니다. 가중치가 미학습 랜덤이라 이건 "정확도가 높다"는 뜻이 아니라 — 양자화·역양자화 스케일 계산이 파이프라인 전체에서 올바르게 맞물려 있다는 자기 정합성(self-consistency) 체크입니다. 클래스 간 점수 차이가 양자화 오차보다 충분히 크면 사소한 수치 차이는 결정(argmax)을 안 바꾸는게 당연하기도 합니다.

4로그 한 줄씩 해설

cuDNN / GPU dlopen 경고 2줄

TensorFlow가 프로세스 시작 시 cuda_executor/gpu_device C++ 백엔드로 CUDA 디바이스를 탐색하는데, 이 venv(~/ladder-litert)엔 cuDNN 같은 CUDA 라이브러리가 LD_LIBRARY_PATH에 없어 탐색이 실패하고 경고를 찍습니다. 이 프로젝트의 다른 문서(01_environment_setup.md 3-4-a절)에서 다룬 것과 같은 근본 원인 계열(venv에 묶여 있는 CUDA 관련 라이브러리가 로더 경로 밖에 있음)이지만 결과는 정반대입니다:

사례영향받는 것결과
~/emb-ai venv, ONNX Runtime CUDA/TensorRT EP실제 추론 실행 경로치명적 — 조용히 CPU로 폴백, 지연시간이 GPU 대비 수 배~수십 배 나빠짐(실측: TensorRT 0.41ms→11.83ms)
~/ladder-litert venv, 이번 변환 스크립트없음 — TFLiteConverter는 그래프 재작성/양자화 파라미터 계산만 수행무해 — CUDA 커널을 한 번도 호출하지 않는 순수 CPU 작업이라 경고만 찍히고 결과에 영향 없음

즉 "같은 클래스의 원인이 어디서는 치명적이고 어디서는 무해하다"는 것 자체가 포인트입니다 — 무엇이 GPU를 실제로 쓰는지가 경고의 심각도를 가릅니다. 사용자가 로그에 남긴 자체 진단("변환 작업 자체는 CPU로도 무관")이 정확히 이 구분을 짚은 것입니다.

fully_quantize: 0, inference_type: 6, ... 라인

확인됨 input_inference_type: INT8, output_inference_type: INT8은 스크립트의 conv.inference_input_type = tf.int8 / conv.inference_output_type = tf.int8 설정과 정확히 일치하고, §1에서 실측한 입력 텐서의 dtype=int8로도 재확인됩니다.

불확실 fully_quantize가 0(false)으로 찍힌 이유와 inference_type: 6이라는 정수 enum이 내부적으로 정확히 무엇을 가리키는지는 이번 조사로 권위 있게 확정하지 못했습니다. 정황상 fully_quantize는 MLIR 양자화기의 파라미터로, "모델 본문뿐 아니라 입출력까지 양자화하는가"를 나타내는 것으로 보이는데 — 구버전 API는 이걸 단일 플래그로 노출했지만, 지금 쓰는 최신 파이썬 API(inference_input_type/inference_output_type을 별도 필드로 설정)에서는 그 경로를 안 타서 0으로 남는 것으로 추정됩니다. 다만 이 추정을 1차 소스로 확정 검증하지는 못했으므로, 이 문단은 추정으로 남깁니다 — 위 두 *_inference_type: INT8 필드만 확정된 사실입니다.
