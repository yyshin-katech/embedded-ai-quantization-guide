ARM Cortex-A 폴백 (2) — 빈 사분면을 채우다: dotprod 없는 A53

앞선 CPU 폴백 프록시 (1)은 부호 반전을 ARM(Pi 5·dotprod 있음) vs x86(VNNI 없음) 축에서 보였다. 남은 질문은 "부호를 가르는 게 ISA 계열(ARM/x86)인가, dot-product 명령 유무인가?"였다. 이를 가르려면 dotprod 없는 ARM이 필요했다 — NXP i.MX8M Nano의 Cortex-A53(ARMv8.0-A, asimddp 없음, NPU 없음)이 정확히 그 빈칸이다. 같은 ResNet50 INT8 QDQ를 실기(실물 EVK)에서 CPUExecutionProvider로 관통시킨 결과: A53는 INT8이 1.65× 느려진다. → 부호를 가르는 건 ISA 계열이 아니라 dot-product 명령의 유무임을 ARM 내부(A76 vs A53)에서 확정.

CPU 폴백 프록시 (1)이 남긴 빈칸 "dot-product 없는 ARM"을 실물 i.MX8M Nano EVK(Cortex-A53)로 채웠다. 결과는 통념("ARM이면 INT8이 유리")을 ARM 안에서 반박한다: 같은 INT8 그래프가 A76에선 빨라지고 A53에선 느려진다 — 갈림은 코어에 asimddp(SDOT)가 있느냐 없느냐다.

발견 1 · 부호는 dotprod가 가른다이제 세 사분면이 채워졌다 — Pi 5 A76(asimddp 있음) INT8 ×1.83 빠름 · i.MX8M A53(asimddp 없음) INT8 1.65× 느림 · x86 i9(VNNI 없음) INT8 1.76× 느림. A76과 A53는 같은 ARMv8 계열인데 부호가 갈린다 → 결정 인자는 "ARM이냐 x86이냐"가 아니라 정수 dot-product 명령(SDOT/UDOT/VPDPBUSD)의 유무임이 확정.
발견 2 · FP32는 3-플랫폼 비트 동일같은 1,000장·같은 CPUEP로 세 플랫폼(ORT 1.17.1/1.23.2/1.28.0) 예측을 1:1 대조: FP32는 세 쌍 모두 1000/1000(100%) — 서로 다른 ORT 버전·ISA에서도 완전 동일. 반면 INT8은 imx↔pi5 965/1000·imx↔x86 961/1000(≈96%)로 갈린다. 버전이 아니라 INT8 정수 경로의 ISA 민감성이 원인임을 3-플랫폼으로 재확증.
발견 3 · 2GB no-swap · ORT 1.17.1 벽 2건실물 저사양 보드라 프록시 (1)엔 없던 벽 2건이 나왔다 — (a) 2GB LPDDR4·swap 0에서 FP32가 602MB float32 배열을 올리다 OOM(rc=137) → rpi_bench_lowmem.py(이미지 1장씩 lazy 전처리, 결과 비트 동일)로 해소; (b) INT8 QDQ의 opset_import가 미사용 ai.onnx.ml v5를 선언 → ORT 1.17.1(ai.onnx.ml 상한 4)이 로드 거부 → 미사용 opset 항목 제거(415 노드 전부 기본 도메인 → 연산 불변)로 해소.
캐비앗(먼저) i.MX8M Nano는 ARM Cortex-A 폴백 프록시일 뿐 자동차 NPU가 아니다 — Nano엔 애초에 NPU가 없어(i.MX8M Plus에만 있음) CPU 경로가 유일하다. 측정한 건 "모든 op가 CPU로 폴백됐을 때의 바닥값"이다. 또한 절대 지연·top-1은 CPUEP · wall-clock 단일입력 · 배치1 · 1,000장 서브셋 · ORT 버전 상이(1.17.1/1.23.2/1.28.0) 기준이라 상대 관계(부호·배율·예측 일치율)만 유효하다. A53↔A76↔x86 절대 속도 비교는 서로 다른 급의 기계라 논점이 아니다.

§3 — 부호 반전 3-사분면 완성: 부호는 dot-product 명령이 가른다 (핵심)

아래 막대는 각 플랫폼을 자기 자신의 FP32 = 1.00×로 정규화한 상대 지연이다(절대 지연은 A53 ≫ Pi5 ≫ x86 순이지만, 서로 다른 급의 기계라 논점이 아니다). 세로 점선(1.0×)이 "자기 FP32" 기준선 — 왼쪽에 멈추면 INT8이 빠른 것, 넘어서면 느린 것이다. 위에서부터 dotprod 있음(A76) → 없음(A53) → VNNI 없음(x86) 순으로, 가속 명령이 사라지는 순간 부호가 뒤집힌다.

왜 A53만 느려지나 ONNX Runtime CPU 커널(MLAS)은 INT8 QLinearConv/MatMulInteger를 정수 dot-product 명령이 있으면 그걸로 가속한다 — ARM은 SDOT/UDOT(asimddp, ARMv8.2+), x86은 VPDPBUSD(VNNI). A76엔 asimddp가 있어 INT8 conv가 FP32보다 빠르지만, A53은 ARMv8.0이라 그 명령이 아예 없다 — INT8 경로가 스칼라/일반 SIMD로 떨어지고 그 위에 QuantizeLinear/DequantizeLinear 노드 비용까지 얹혀 FP32보다 되레 1.65× 느려진다. x86 i9(VNNI 없음)와 같은 메커니즘·같은 부호다. 즉 A76 vs A53는 "ARM이라서"가 아니라 ARMv8.2의 dotprod 확장을 코어가 구현했는지 하나로 갈린다.
실무 함의 오토모티브 SoC의 A-코어는 세대가 섞여 있다 — 최신 A76/A78(dotprod ○)도, 구형 A53/A72(dotprod ×)도 흔하다. NPU가 못 받아 CPU로 폴백된 op가 A53 같은 구형 코어에 떨어지면 INT8이 되레 독이 된다(양자화가 손해). 폴백 비중이 큰 파이프라인일수록 타깃 A-코어의 ISA 레벨(ARMv8.0 vs 8.2+)을 먼저 확인해야 한다. i.MX8M Nano는 그 "구형 A-코어 폴백"의 실물 하한선이다.

§4 — 크로스플랫폼 예측 일치: FP32는 3-플랫폼 비트 동일, INT8은 아니다

해석 FP32는 IEEE-754 연산이 세 ISA에서 사실상 동일 순서로 수행돼 1,000장 전부 같은 예측이 나온다 — ORT 버전이 셋 다 달라도(1.17.1/1.23.2/1.28.0) 100% 일치라, "CPUEP FP32는 크로스플랫폼 동일"이 문자 그대로 성립하고 버전은 주범이 아님이 재확증된다. 그러나 INT8 QDQ는 다르다: 정수 누산·재양자화 반올림이 SDOT(A76)·스칼라 정수(A53)·AVX2 정수(x86)에서 미세하게 갈려 3~4%가 뒤집힌다. 순 top-1 영향은 작지만(셋 다 ≈0.75), "INT8은 FP32보다 수치가 ISA에 민감"이 이제 세 점으로 확립됐다 — 서로 다른 타깃에서 INT8 정확도를 비트 단위로 기대하면 안 된다.

§5 — 실물 저사양 보드의 벽 2건: 2GB no-swap · ORT 1.17.1

프록시 (1)의 Pi 5(8GB·최신 ORT)엔 없던 벽이, 실물 2GB·swap 0·ORT 1.17.1 보드에서 두 개 나왔다. 둘 다 결과를 바꾸지 않는 최소 수정으로 해소했고, 그 과정 자체가 엣지 배포의 교훈이다.

벽 1 — FP32 OOM: 2GB no-swap에서 602MB 배열이 SIGKILL
# 첫 실행: FP32가 (1000,3,224,224) float32 배열(≈602MB)을 한 번에 올리다 사망
$ cat run.log
[fp32] begin ...
[fp32] done rc=137              # 137 = 128+9 = SIGKILL = OOM killer
$ free -m
              total   used   free
Mem:           1985   ...
Swap:            0      0      0      # swap 없음 → 스래싱 없이 즉시 kill

# 해소: rpi_bench_lowmem.py — uint8 캐시를 mmap, 이미지 1장씩 lazy 전처리
#       (1000,3,224,224) float32를 절대 materialize 안 함. 전처리는 elementwise라
#       예측은 비트 동일. peak RSS ≈ 602MB → ≈333MB, 보드가 살아있음
$ python3 rpi_bench_lowmem.py --model resnet50_fp32.onnx ...
[aarch64] fp32: median=680.2026ms top1=0.7620 rc=0
벽 2 — INT8 opset skew: 미사용 ai.onnx.ml v5를 ORT 1.17.1이 거부
# 첫 실행: INT8 모델 로드가 opset에서 죽음
$ python3 rpi_bench_lowmem.py --model resnet50_int8_qdq.onnx ...
... Opset 5 is under development and support for this is limited.
Current official support for domain ai.onnx.ml is till opset 4.   # ORT 1.17.1 상한

# 진단: opset_import엔 ai.onnx.ml v5(+training·com.microsoft·org.pytorch.aten)가
#       찍혀 있지만, 실제 415개 노드는 전부 기본 도메인('')만 쓴다 — 떠도는 스탬프
>>> {op.domain: n for ...} → {'': 415}   # ai.onnx.ml 노드 0개

# 해소: 미사용 opset_import 항목 제거, ('', 17)만 남김 → 연산 그래프 불변

>>> onnx.checker.check_model(m)      # PASS, 415 노드 보존
$ python3 ... --model resnet50_int8_qdq_op4.onnx ...

왜 중요한가 두 벽 다 exit 0이 아닌 정직한 실패(rc=137 / 로드 예외)라 조용히 틀리지는 않았다 — 하지만 양쪽 수정 모두 "결과를 바꾸지 않음"을 먼저 증명하고 적용한 게 핵심이다. lowmem은 전처리가 elementwise라 예측 비트 동일, opset strip은 실제 노드가 기본 도메인뿐이라 연산 그래프가 그대로다. 엣지 배포에서 "메모리 상한"과 "런타임 버전의 opset 상한"은 x86 개발기에선 안 보이던 두 벽이며, 실물 보드에서만 드러난다.

§6 — 판정 · 산출물

확정 ✓ 부호를 가르는 건 ISA 계열이 아니라 dot-product 명령

같은 INT8 QDQ·같은 ORT CPUEP인데 A76(dotprod) INT8 ×1.83 빠름 vs A53(no dotprod) INT8 1.65× 느림. A76·A53는 같은 ARMv8 계열이므로, 프록시 (1)의 "ARM이면 빠름" 해석 가능성을 ARM 내부에서 반박한다. 결정 인자는 SDOT/VPDPBUSD 유무 — x86 i9(VNNI 없음)와 A53(dotprod 없음)이 같은 부호를 낸다.

확정 ✓ FP32는 3-플랫폼 비트 동일, INT8은 ISA 민감

서로 다른 ORT 3버전에서 FP32 예측이 세 쌍 모두 1000/1000(100%) → "CPUEP FP32는 크로스플랫폼 동일"이 버전 무관하게 성립. INT8은 ≈96%로 갈려, "INT8 정확도를 비트 단위로 기대 금지"가 세 점으로 확립.

정직화 ✓ i.MX8M Nano는 폴백 프록시일 뿐 NPU 아님

Nano엔 NPU가 없어(Plus에만 탑재) CPU가 유일 경로 — 측정한 건 "구형 A-코어 폴백의 바닥값". 자동차 NPU(QCS8550/RZ-V2H/TDA4VM) 가속 수치는 전이되지 않는다. Qualcomm HTP 실측은 별도 보고서에서 이미 벤더 NPU 축을 채웠고, 이 A53 바닥값은 그 대척점(offload 0%·구형 코어)이다.
