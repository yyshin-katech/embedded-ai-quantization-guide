DEEPX DX-M1 — DETR INT8: 폭락 없음, 단 트랜스포머를 양자화 안 하기 때문

CNN 축(분류 ResNet50 무손실 · 검출 yolo26n −2.0%)을 트랜스포머 검출기 facebook/detr-resnet-50로 확장 — 핵심 질문: stage2 ORT/TRT −42.9%·Jetson TRT-sym −43.8%의 트랜스포머 INT8 폭락이 DX-M1 native PTQ에서도 재현되는가? 답=아니오(−0.2%, 노이즈 내). 그러나 레짐 프로파일러가 이유를 뒤집는다: dx_com의 자동 파티션이 CNN 백본 + 첫 encoder self-attention만 NPU INT8로, 트랜스포머의 나머지 전체를 호스트 CPU FP32로 밀어낸다 → 폭락이 없는 건 DX-M1이 트랜스포머를 잘 양자화해서가 아니라 아예 안 하기 때문. 대가는 910ms 호스트 FP32 트랜스포머 → E2E 1.04s, host-CPU-compute-bound(제3의 레짐).

세 벤더-NPU 축이 이제 분류(ResNet50)·CNN 검출(yolo26n)·트랜스포머 검출(DETR)을 덮는다. DETR가 폭락하지 않는다는 결과는 겉보기엔 승리, 실제론 회피 — §2가 레짐 프로파일러로 증명하듯 트랜스포머는 애초에 INT8이 되지 않았다(호스트 FP32). 즉 이 축은 "DX-M1이 트랜스포머 INT8을 어떻게 하나"가 아니라 "벤더 툴체인이 양자화 불가한 트랜스포머를 만나면 어떻게 하나"에 답한다 → 조용히 호스트로 밀어 정확도를 지키고 지연을 지불한다.

1 · 정확도 — 트랜스포머 INT8 폭락이 재현되지 않는다

주의 — 승리 아님 이 −0.2%는 백본 INT8 오차뿐이다. FP32 레퍼런스도, NPU 배포본도 트랜스포머는 둘 다 FP32(§2) → 이 축은 DX-M1에서 트랜스포머 INT8을 시험하지 않는다. "무손실"은 트랜스포머를 양자화 안 한 결과이지 잘 한 결과가 아니다. stage2/Jetson이 트랜스포머를 강제 INT8해 폭락한 것과 같은 사실의 양면: 트랜스포머 activation은 INT8을 못 견딘다 — 그래서 양자화하면 폭락, 안 하면 FP 지연.

2 · 메커니즘 — dx_com은 트랜스포머를 호스트 FP32로 민다 (헤드라인)

결정적 관찰 — dxbenchmark를 --use-ort 없이 돌리면("only NPU tasks operate") NPU 그룹의 실제 출력 텐서가 드러난다: 그래프는 첫 encoder self-attention의 softmax에서 잘린다.

dxbenchmark --dir . (--use-ort 없이) — npu_0 태스크의 입출력
Task[0] npu_0, NPU, input 2,558,400 B, output 23,990,400 B
  Inputs
    - pixel_values                                    UINT8 [1, 800, 1066, 3]
  Outputs
    - /model/Transpose_output_0                       FLOAT [1, 850, 256]   # 백본 feature (850=25×34 토큰)
    - /model/encoder/layers.0/self_attn/Softmax_out.. FLOAT [1, 8, 850, 850] # 첫 attention 맵 (23.1MB!)
  # 여기까지가 NPU INT8. 이후 전부 호스트 CPU FP32(ORT).

즉 NPU INT8 그룹 = CNN 백본(ResNet50) + 첫 encoder self-attention(softmax까지), 그리고 CPU 그룹 = 나머지 트랜스포머 전체(encoder 나머지 + decoder 6층 + FFN + 예측 헤드)를 호스트 A76에서 FP32 ORT로. 컴파일 로그의 Marked 2 MemoryOp(s) from NPU to CPU · 1 NPU groups, 1 CPU groups가 바로 이 절단이다(그 2개 MemoryOp = 위 2개 handoff 텐서). --use-ort on/off 토글이 두 부분의 시간을 직접 분해한다:

dxbenchmark 모드무엇이 도나FPSE2E 지연NPU 연산

왜 여기서 자르나 dx_com의 "infection"은 NPU가 배치 못 하는 op(동적 [850,850] attention 계열)을 만나면 그 지점을 CPU로 표시하고 전파한다 → 트랜스포머 거의 전체가 CPU 그룹이 된다. 이는 Jetson DLA(트랜스포머 404조각/16 ForeignNode)·TRT(Gemm 전용 INT8)와 같은 근본(NPU op 커버리지)이나 결과가 다르다: 실패·파편화 대신 작동하는 하이브리드(NPU 백본 INT8 + 호스트 트랜스포머 FP32)를 낸다. 정확도는 지키고, 지연을 문다.

제3의 레짐 DX-M1의 병목이 모델마다 다른 스테이지로 옮겨간다 — 크로스오버 축은 이를 compute(NPU) ↔ D2H(PCIe) 두 레짐으로 봤다. DETR는 세 번째를 연다: host-CPU-compute-bound. 천장이 하드웨어(NPU·PCIe)가 아니라 벤더 컴파일러가 호스트로 민 FP32 트랜스포머다. NPU 코어 수를 늘려도 무의미(NPU는 4%) — 천장은 A76 단일스레드 ORT.

4 · 3-모델 종합 — 같은 DX-M1·같은 Pi5, 세 태스크 세 레짐

ResNet50CNN 분류0.7620 → 0.7660무손실 (~0)NPU-compute-bound (3코어 2.19×)

DETR-R50트랜스포머 검출0.4377 → 0.4385"무손실"* (−0.2%)host-CPU-bound (트랜스포머 FP32, NPU 4%)

* DETR의 "무손실"엔 별표가 붙는다: CNN 두 모델은 전체가 NPU INT8이라 무손실이 진짜 양자화 강건성이지만, DETR는 트랜스포머가 NPU INT8이 아니라(호스트 FP32) 무손실이다. 세 레짐이 셋 다 다른 물리적 천장을 가리킨다 — NPU 연산 / PCIe 대역 / 호스트 CPU. 크로스오버 축의 "천장은 하드웨어 아닌 모델(출력 크기)"에, DETR는 "때론 천장이 벤더가 호스트로 민 부분"을 더한다.

가이드 연결 이 축은 stage2 §4.5의 "범인=activation 분산"을 벤더-NPU 관점에서 완성한다: 트랜스포머 activation의 넓은 동적 범위 때문에 (1) 강제 INT8하면 폭락(stage2 −42.9%, Jetson −43.8%), (2) SmoothQuant로 입도를 개선하면 부분 회복(Jetson 9%~stage2 59.9%), (3) DX-M1처럼 컴파일러가 손대지 않으면 무손실이나 1.04s. 셋 다 같은 벽의 다른 문이다.

5 · 판정 · 방법 · 캐비앗

헤드라인DETR INT8이 DX-M1서 폭락하지 않음(−0.2%) — 단 dx_com이 트랜스포머를 호스트 FP32로 밀기 때문(NPU=백본만 INT8). 폭락(강제 INT8)과 무폭락(자동 회피)은 activation 벽의 양면.
파티션 (증거)708 노드 → NPU 출력 = Transpose[1,850,256] + enc.layers.0.self_attn.Softmax[1,8,850,850](FLOAT). 나머지 트랜스포머 = 호스트 CPU FP32(ORT). --use-ort on/off = 1.10 vs 17.55 fps.
레짐host-CPU-compute-bound: CPU 트랜스포머 910.6ms=87.9% ≫ D2H 57.3ms ≫ NPU INT8 41.1ms=4% ≫ H2D 7ms. 제3의 DX-M1 레짐.
양자화 격리FP32 ref와 NPU가 같은 detr_2out.onnx 그래프(양자화만 차이)·비트동일 500장·같은 스코어러 → Δ는 백본 INT8 오차만.
방법 함정dx_engine 입력 계약 = uint8 NHWC [1,800,1066,3] RGB(div/normalize/transpose fold, convertColor/expandDim skip). DETR 2출력은 순서 미보장 → 원소 수(9200 vs 400)로 판별. 4출력 export leftover(encoder_hidden_states 870KB)는 onnx.utils.extract_model로 2출력만 남겨 D2H 팽창 차단.
